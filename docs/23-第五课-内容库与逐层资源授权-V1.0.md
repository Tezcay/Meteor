## 1. 用户在内容库做了什么

第四课结束后，订单为 `PAID`，对应 `EntitlementGrant` 为 `ACTIVE`。用户进入 `/library` 后可以：

1. 查看当前仍有效的购买权益卡片。
2. 从卡片跳回来源订单详情。
3. 展开当前套餐的全部正式 Release。
4. 选择某个 Release 展开冻结文件清单。
5. 查看文件用途、文件名、媒体类型、大小和 SHA-256 摘要。

当前 Manifest 接口仍只返回文件元数据，不返回文件内容、内部存储键或下载凭证。页面在元数据旁提供下载按钮，按钮另行调用授权 POST，再使用返回的一次性 URL 获取文件。

页面层级：

```text
内容库 /library
  └─ LibraryItemCard：一份 ACTIVE Grant
       └─ ReleaseExplorer：该 Grant 对应 Package 的正式版本
            └─ DeliveryManifestPanel：一个 Release 的冻结文件清单
                 └─ ManifestItem：清单里的一个文件条目
```

这套组件层级直接对应后端领域关系，页面状态不再全部堆在 `AccountPages.vue` 中。

## 2. 三条 GET 请求组成完整读取链

```mermaid
flowchart LR
    A[/library] --> B[GET /api/library]
    B --> C[LibraryController]
    C --> D[LibraryService]
    D --> E[EntitlementMapper]
    E --> F[(ACTIVE grants + order snapshot)]

    G[展开版本] --> H[GET /api/library/grantId/releases]
    H --> I[ReleaseController]
    I --> J[ReleaseService]
    J --> K[先查 ACTIVE Grant]
    K --> L[按可信 packageId 查 PUBLISHED releases]

    M[展开文件清单] --> N[GET /api/library/grantId/releases/releaseId/manifest]
    N --> O[DeliveryManifestController]
    O --> P[DeliveryManifestService]
    P --> Q[先查 ACTIVE Grant]
    Q --> R[校验 Release 属于 Grant 的 Package]
    R --> S[查询 ManifestItem + FileObject 元数据]
```

三个请求都从当前 Session 用户出发。后两个请求里的 `grantId` 和 `releaseId` 来自浏览器，只能作为待验证标识。

### 2.1 请求一：读取内容库

```http
GET /api/library
Cookie: JSESSIONID=...
```

### 2.2 请求二：读取可访问版本

```http
GET /api/library/5001/releases
Cookie: JSESSIONID=...
```

### 2.3 请求三：读取冻结清单

```http
GET /api/library/5001/releases/3001/manifest
Cookie: JSESSIONID=...
```

GET 请求不需要修改数据，当前共享 Client 不为它们获取 CSRF token。Session Cookie 仍必须携带，Spring Security 才能恢复用户身份。

本节可以停在这里。恢复时从三个 URL 画出三层箭头。

## 3. 内容库怎样只读取当前有效权益

前端 API：`frontend/src/api/library.ts`。

```ts
export async function getLibrary(signal?: AbortSignal) {
  return apiGet<LibraryItemResponse[]>('/api/library', signal)
}
```

Controller：`backend/src/main/java/dev/meteor/entitlement/controller/LibraryController.java`。

```java
@GetMapping
public List<LibraryItemResponse> getLibrary(
        @AuthenticationPrincipal MeteorUserPrincipal principal
) {
    return libraryService.getLibrary(principal.id());
}
```

Service：

```java
@Transactional(readOnly = true)
public List<LibraryItemResponse> getLibrary(long userId) {
    return entitlementMapper.findActiveLibraryByUserId(userId).stream()
            .map(LibraryService::toResponse)
            .toList();
}
```

Mapper 核心条件：

```sql
WHERE eg.user_id = #{userId}
  AND eg.status = 'ACTIVE'
ORDER BY eg.granted_at DESC, eg.id DESC
```

### 3.1 空内容库返回什么

用户没有 ACTIVE Grant 时 Mapper 返回空列表，接口响应 200 和 `[]`。这是合法空状态，页面显示“内容库还是空的”，无需用 404 表达。

### 3.2 卡片标题来自哪里

SQL 连接：

```sql
FROM entitlement_grants eg
JOIN order_items oi ON oi.id = eg.order_item_id
JOIN orders o ON o.id = oi.order_id
```

卡片的 `product_title`、`shop_name`、`package_name` 来自 `order_items` 成交快照。商品后来改名或套餐调价时，内容库仍能说明用户当时买了什么。

### 3.3 `@Transactional(readOnly = true)`

这个方法只查询。`readOnly = true` 向事务框架和数据库驱动表达只读意图，也让代码审查者快速识别方法边界。权限仍由 SQL 条件保证，注解本身不会自动增加用户过滤。

## 4. 内容库和订单历史回答不同问题

[ADR-0001](adr/0001-content-library-shows-active-access-only.md) 固定了当前规则：

```text
内容库：我现在能访问什么？
订单历史：我过去买过什么，当前订单与权益状态是什么？
```

因此：

- `/api/library` 只返回 `ACTIVE` Grant。
- `/api/orders` 和 `/api/orders/{id}` 使用 `LEFT JOIN entitlement_grants`，可以显示 `ACTIVE`、`REVOKED` 或尚无权益。
- Grant 被撤销后，从内容库消失，但订单和购买快照仍保留。

页面曾经展示过某项内容不能作为后续授权依据。读取 Release、Manifest，以及每次下载，都要重新检查 Grant 当前仍是 ACTIVE。

### 4.1 为什么不删除撤销记录

保留 `REVOKED` Grant 可以说明：

- 权益来源是哪一个订单项。
- 何时授予、何时撤销。
- 订单历史为什么不再具有访问权限。

删除记录会损失审计事实，也容易让退款、申诉和重复购买的判断失去依据。

### 4.2 当前撤销边界

数据库模型和订单页面已能表达 REVOKED；完整退款接口、自动撤权流程和退款状态机尚未实现。教程不能把可表达状态写成已经完成的退款业务。

## 5. 七个领域对象怎样连接

| 对象 | 当前职责 | 关键关联 |
| --- | --- | --- |
| Product | 对外展示的稳定商品身份 | 一个 Product 有多个 Package |
| Package | 可购买的内容档位 | 一个 Package 有多个 Release |
| EntitlementGrant | 某次订单项授予用户的访问资格 | 指向用户、订单项、Product、Package |
| Release | Package 的一次正式发布 | 归属一个 Package |
| DeliveryManifest | Release 冻结时的完整文件清单 | 一个 Release 最多一个 Manifest |
| ManifestItem | 清单里的有序业务条目 | 连接 Manifest 与 FileObject |
| FileObject | 内容固定的文件对象及可信元数据 | 可以被多个 ManifestItem 引用 |

关系图：

```text
User
  └─ EntitlementGrant ── OrderItem
          │
          └─ Package
               └─ Release
                    └─ DeliveryManifest
                         └─ ManifestItem
                              └─ FileObject
```

### 5.1 为什么 Grant 指向 Package

用户购买的是 Basic 或 Pro 等具体档位。两个档位即使属于同一 Product，文件范围也不同。Release 归属 Package，授权就能准确停在购买档位内。

### 5.2 `ALL_RELEASES`

当前唯一访问策略是 `ALL_RELEASES`。有效 Grant 可以读取对应 Package 当前所有 `PUBLISHED` Release，包括购买前已有版本和购买后新增版本。

Service 当前没有策略分支，因为数据库检查约束只允许 `ALL_RELEASES`。以后加入“仅购买时版本”或“限期更新”时，需要新增明确策略、截止字段、迁移和测试。

## 6. Release 接口先验证 Grant

Controller：

```java
@RequestMapping("/api/library/{grantId}/releases")
```

Service：

```java
EntitlementGrantProjection grant = entitlementMapper
        .findActiveByIdAndUserId(grantId, userId)
        .orElseThrow(() -> new EntitlementGrantNotFoundException(grantId));

List<ReleaseProjection> releases = releaseMapper
        .findPublishedByPackageId(grant.packageId());
```

第一条查询要求：

```sql
WHERE id = #{grantId}
  AND user_id = #{userId}
  AND status = 'ACTIVE'
```

只有验证通过后，Service 才从 Grant 取得可信 `packageId`。接口没有接受浏览器提交的 packageId。

### 6.1 三种情况统一 404

下面三种情况都查不到有效 Grant：

- grantId 不存在。
- Grant 属于其他用户。
- Grant 已是 REVOKED。

共享异常处理器返回 404 `ENTITLEMENT_NOT_FOUND`。统一响应减少外部用户枚举其他账号购买信息的机会。

### 6.2 验证失败后不查 Release

Service 在 Grant 查询失败时立即抛异常。对应测试检查 `releaseMapper.calls` 为 0，证明后续查询没有执行。

## 7. Release SQL 和“最新版本”

Mapper：

```sql
SELECT id,
       package_id,
       release_number,
       version_label,
       summary,
       published_at
FROM releases
WHERE package_id = #{packageId}
  AND status = 'PUBLISHED'
ORDER BY release_number DESC, id DESC;
```

只返回：

- Grant 对应 Package。
- 状态为 `PUBLISHED`。

`DISABLED` Release 不进入列表。商品是否仍在售不会参与老用户版本读取；商品下架影响新购买，Release 禁用影响具体交付版本，两者边界不同。

### 7.1 `latest` 不在表里

Service 遍历已经降序排列的列表：

```java
for (int index = 0; index < releases.size(); index++) {
    ReleaseProjection release = releases.get(index);
    result.add(new ReleaseResponse(
            release.id(),
            release.packageId(),
            release.releaseNumber(),
            release.versionLabel(),
            release.summary(),
            release.publishedAt(),
            index == 0
    ));
}
```

`index == 0` 的第一项被标记为最新。这个结果依赖 SQL 按 `release_number DESC` 排序；测试同时固定顺序和 latest 标记。

### 7.2 空版本列表

Grant 有效但 Package 还没有 PUBLISHED Release 时，返回 200 和空数组。页面显示“当前套餐还没有可用的正式版本”。

## 8. V9 怎样约束 Package Release

文件：`backend/src/main/resources/db/migration/V9__create_package_releases.sql`。

核心字段：

```text
package_id
release_number
version_label
summary
status
published_at
disabled_at
```

关键约束：

```sql
UNIQUE (package_id, release_number)
UNIQUE (package_id, version_label)
CHECK (release_number > 0)
CHECK (status IN ('PUBLISHED', 'DISABLED'))
```

状态与时间约束：

```sql
CHECK (
    (status = 'PUBLISHED' AND disabled_at IS NULL)
    OR
    (status = 'DISABLED' AND disabled_at IS NOT NULL)
)
```

同一个 Package 内版本序号和标签唯一；不同 Package 可以各自有 `1.0.0`。

V9 预置：

```text
Basic / Release #3001 / 1.0.0
Pro   / Release #3002 / 1.0.0
```

当前没有创作者 Release 写接口、草稿或审核流程。迁移中预置的两条正式 Release 用于真实读取链路和学习验收。

## 9. Manifest 接口再次验证两层归属

URL 同时含两个浏览器可修改的 id：

```text
/api/library/{grantId}/releases/{releaseId}/manifest
```

Service 第一步仍查当前用户的 ACTIVE Grant：

```java
EntitlementGrantProjection grant = entitlementMapper
        .findActiveByIdAndUserId(grantId, userId)
        .orElseThrow(() -> new EntitlementGrantNotFoundException(grantId));
```

第二步使用 Grant 中的 Package 校验 Release：

```java
DeliveryManifestProjection manifest = manifestMapper
        .findPublishedByReleaseIdAndPackageId(
                releaseId,
                grant.packageId()
        )
        .orElseThrow(() -> new DeliveryManifestNotFoundException(releaseId));
```

对应 SQL：

```sql
FROM delivery_manifests dm
INNER JOIN releases r ON r.id = dm.release_id
WHERE r.id = #{releaseId}
  AND r.package_id = #{packageId}
  AND r.status = 'PUBLISHED'
```

### 9.1 Basic Grant 不能读取 Pro Release

假设：

```text
Grant #5001 → Basic Package #2001
Pro Release #3002 → Pro Package #2002
```

用户把 URL 中 releaseId 改为 3002，查询仍带 `package_id = 2001`，所以返回空。共享异常处理器响应 404 `DELIVERY_MANIFEST_NOT_FOUND`。

### 9.2 为什么不直接按 releaseId 查询

releaseId 只证明“请求了哪个版本”，无法证明“当前 Grant 有权访问这个版本”。把 Package 条件放入同一 SQL，能在数据库读取阶段阻止跨套餐资源访问。

### 9.3 先验证 Grant 再查 Manifest

Grant 无效时，测试确认 Manifest 头和条目查询次数都是 0。Release 跨套餐时，只执行头查询，不继续读取文件条目。

## 10. ManifestItem 与 FileObject 返回哪些字段

Manifest 头验证成功后查询条目：

```sql
SELECT mi.id,
       mi.item_position AS position,
       mi.role,
       mi.display_name,
       fo.original_filename AS filename,
       fo.media_type,
       fo.size_bytes,
       fo.content_sha256 AS sha256
FROM manifest_items mi
INNER JOIN file_objects fo ON fo.id = mi.file_object_id
WHERE mi.manifest_id = #{manifestId}
ORDER BY mi.item_position, mi.id;
```

对外响应字段：

```text
position
role
displayName
filename
mediaType
sizeBytes
sha256
```

没有返回：

```text
storage_provider
storage_key
本地 Classpath 路径
永久文件 URL
```

### 10.1 三类条目角色

```text
PRIMARY：主要文件
GUIDE：使用指南
BONUS：附加内容
```

角色用于页面解释文件用途，不能代替下载权限判断。

### 10.2 汇总怎样计算

Service 映射条目后计算：

```java
long totalBytes = items.stream()
        .mapToLong(ManifestItemResponse::sizeBytes)
        .sum();
```

返回：

```java
new DeliveryManifestResponse(
        manifest.id(),
        manifest.releaseId(),
        manifest.versionLabel(),
        manifest.createdAt(),
        items.size(),
        totalBytes,
        items
)
```

空 Manifest 返回 `itemCount = 0`、`totalBytes = 0` 和空数组，Service 不虚构文件。

### 10.3 SHA-256 的范围

SHA-256 用于标识和核对文件内容。相同字节应得到相同摘要；文件变化会得到不同摘要。

摘要不授予访问权限，也不证明发布者身份。未来下载仍要重新校验 Session、Grant、Release、ManifestItem 和文件状态。

## 11. V10 的四层交付表

文件：`backend/src/main/resources/db/migration/V10__create_delivery_manifests.sql`。

### 11.1 `file_objects`

保存物理文件身份和可信元数据：

```text
storage_provider
storage_key
original_filename
media_type
size_bytes
content_sha256
```

约束：存储提供方加存储键唯一；字节数大于 0；SHA-256 长度为 64。

### 11.2 `delivery_manifests`

一行代表一个 Release 的冻结清单头：

```sql
UNIQUE (release_id)
```

当前一个 Release 最多一份 Manifest。

### 11.3 `manifest_items`

连接 Manifest 和 FileObject，并保存位置、角色和展示名：

```sql
UNIQUE (manifest_id, item_position)
UNIQUE (manifest_id, file_object_id)
```

同一清单不能重复位置，也不能重复引用同一文件对象。

### 11.4 FileObject 可以复用

V10 中同一个 `usage-guide.md` 同时进入 Basic 与 Pro 的 Manifest。物理文件元数据只保存一份，两个 ManifestItem 分别表达它在各自清单中的业务位置。

### 11.5 当前素材范围

当前 `storage_provider` 是 `CLASSPATH`，对应仓库中的学习用交付素材。迁移保存了真实字节数和 SHA-256；下载服务读取文件后会再次核对这两项。生产对象存储、上传、病毒扫描、大文件流式传输和断点续传尚未实现。

## 12. 前端为什么拆成三层组件

### 12.1 `AccountPages.vue`

负责页面路由级状态：

- `/library` 加载内容库。
- `/orders` 加载订单列表。
- `/orders/{id}` 加载订单详情。
- 页面级 loading、error、empty 和首屏数据。

它不再管理每个 Grant 的 Release 请求和每个 Release 的 Manifest 请求。

### 12.2 `LibraryItemCard.vue`

负责一份 Grant 卡片：

- 展示成交快照和来源订单。
- 管理版本区域展开／收起。
- 第一次展开时挂载 `ReleaseExplorer`。

### 12.3 `ReleaseExplorer.vue`

负责一份 Grant 下的 Release：

- 调用版本 API。
- 展示 loading、error、empty、success。
- 标记当前展开的 Release。
- 为已经打开过的 Release 保留 Manifest 面板实例。

### 12.4 `DeliveryManifestPanel.vue`

负责一对 `grantId + releaseId`：

- 调用 Manifest API。
- 展示清单汇总和文件元数据。
- 管理自己的加载、失败与重试。

组件按业务对象拆分后，一个 Manifest 请求失败不会覆盖另一个 Release 的数据；页面级订单请求也不会取消子组件请求。

## 13. 第一次展开、收起和再次展开

`LibraryItemCard`：

```ts
const expanded = ref(false)
const hasOpened = ref(false)

function toggleReleases() {
  expanded.value = !expanded.value
  if (expanded.value) hasOpened.value = true
}
```

模板：

```vue
<ReleaseExplorer
  v-if="hasOpened"
  v-show="expanded"
  :grant-id="item.grantId"
  :region-id="releaseRegionId"
/>
```

### 13.1 `v-if` 的作用

第一次展开前 `hasOpened` 为 false，组件没有挂载，因此不会请求版本。

第一次展开后 `hasOpened` 永久为 true，组件被创建，`useKeyedLoader` 的立即 watcher 发起请求。

### 13.2 `v-show` 的作用

收起时组件仍存在，只通过 CSS 隐藏。再次展开会使用已经取得的数据，不重复请求。

如果这里继续使用随 `expanded` 变化的 `v-if`，每次收起都会卸载，重新展开会创建新实例并再次请求。

### 13.3 Manifest 面板怎样保留

`ReleaseExplorer` 保存：

```ts
const expandedReleaseId = ref<number | null>(null)
const openedReleaseIds = ref(new Set<number>())
```

- `expandedReleaseId` 控制当前可见的一个面板。
- `openedReleaseIds` 记录哪些 Release 已经打开过。
- 第一次打开某 Release 时才挂载其 `DeliveryManifestPanel`。
- 收起后使用 `v-show` 保留数据。

更新集合时写：

```ts
openedReleaseIds.value = new Set(openedReleaseIds.value).add(releaseId)
```

创建新 Set 引用能明确触发 Vue 响应式更新，也避免直接修改旧集合后难以追踪状态变化。

## 14. `useKeyedLoader` 怎样处理异步竞争

文件：`frontend/src/composables/useKeyedLoader.ts`。

类型签名：

```ts
export function useKeyedLoader<TKey, TValue>(
  key: MaybeRefOrGetter<TKey>,
  loader: (key: TKey, signal: AbortSignal) => Promise<TValue>,
  fallbackMessage: string,
)
```

`TKey` 是请求身份类型，`TValue` 是返回数据类型。同一工具可用于数字 Grant key，也可用于字符串组合 key。

### 14.1 四种状态

```ts
export type LoadStatus = 'idle' | 'loading' | 'success' | 'error'
```

组件根据明确状态互斥显示加载、错误、空结果或数据。

### 14.2 每次加载先取消旧请求

```ts
controller?.abort()
const currentController = new AbortController()
controller = currentController
```

如果 key 改变或用户点击重试，旧 fetch 收到 abort signal。

### 14.3 序号阻止迟到响应覆盖新数据

```ts
const currentSequence = ++sequence
```

请求完成时检查：

```ts
if (currentController.signal.aborted
    || currentSequence !== sequence) return
```

取消信号通常能终止 fetch，但请求可能已经返回，或未来的 loader 未正确响应 abort。序号再做一次逻辑校验，只有最新请求可以写入状态。

示例：

```text
请求 A 开始，sequence = 1
key 改变，请求 B 开始，sequence = 2
请求 B 先完成，写入 B 数据
请求 A 后完成，1 !== 2，结果被丢弃
```

### 14.4 key 变化时清空旧数据

```ts
watch(
  () => toValue(key),
  () => {
    data.value = null
    void load()
  },
  { immediate: true },
)
```

`immediate: true` 让组件挂载后立即加载。key 改变时先清空旧数据，避免新身份加载期间继续显示旧身份内容。

### 14.5 组件卸载时清理

```ts
onBeforeUnmount(cancel)
```

`cancel()` 增加 sequence、终止请求并清空 controller 引用。卸载后的异步结果无法继续写组件状态。

### 14.6 为什么 Manifest 使用组合 key

```ts
const requestKey = computed(
  () => `${props.grantId}:${props.releaseId}`
)
```

Manifest 请求身份由 Grant 和 Release 共同决定。只使用 releaseId 会漏掉“同一 Release 通过哪份 Grant 授权”的变化。

每个 `DeliveryManifestPanel` 实例还有独立的 loader、AbortController、sequence、data 和 error。一个面板重试不会取消另一个面板。

本节可以停在这里。恢复时手工写出 A、B 两个请求乱序完成的 sequence 变化。

## 19. 调试顺序和本课语法

### 19.1 内容库为空

依次检查：

```text
订单是否 PAID
entitlement_grants 是否存在
Grant user_id 是否是当前用户
Grant status 是否 ACTIVE
前端是否请求 GET /api/library
```

订单详情出现 REVOKED 而内容库为空属于当前设计。

### 19.2 展开版本得到 404

检查响应 code：

```text
ENTITLEMENT_NOT_FOUND
```

再核对 Grant 是否存在、属于当前用户、状态 ACTIVE。不要直接从前端传 packageId 绕过 Grant。

### 19.3 Release 有效但列表为空

查询 `releases`：

```text
package_id 是否匹配 Grant
status 是否 PUBLISHED
```

DISABLED Release 被主动过滤。

### 19.4 Manifest 得到 404

如果 Grant 已通过，继续检查：

```text
releaseId 是否存在
Release package_id 是否等于 Grant package_id
Release status 是否 PUBLISHED
delivery_manifests 是否有该 release_id
```

### 19.5 文件列表为空

Manifest 头存在但 `manifest_items` 没有记录时，空数组属于合法数据。检查条目时要同时看 manifest_id、position 与 file_object 外键。

### 19.6 `stream().map().toList()`

Java 代码：

```java
manifestMapper.findItemsByManifestId(manifest.id()).stream()
        .map(DeliveryManifestService::toResponse)
        .toList();
```

- `stream()` 创建处理流水线。
- `map` 把 Projection 转成 Response。
- `ClassName::method` 是方法引用。
- `toList()` 收集结果。

### 19.7 `mapToLong().sum()`

`mapToLong` 产生长整数流，`sum` 返回 long 总和，适合字节数累计。

### 19.8 `shallowRef`

`useKeyedLoader` 使用：

```ts
const data = shallowRef<TValue | null>(null)
```

Loader 每次把完整响应对象替换进去，不需要深层响应式代理每个字段。组件仍能在 `data.value` 整体变化时更新。

### 19.9 `MaybeRefOrGetter`

key 可以是普通值、ref、computed 或 getter。`toValue(key)` 统一读取当前值，让 `useKeyedLoader` 同时适配数字 key 和 computed 组合 key。

### 19.10 `padStart`

文件位置显示：

```ts
String(file.position).padStart(2, '0')
```

位置 1 显示为 `01`，位置 12 保持 `12`。这只改变显示，不改变数据库数值。

## 20. 面试追问与准确回答

### 问：内容库为什么只显示 ACTIVE Grant？

答：

> 内容库表达当前可访问内容，所以 SQL 同时限定当前 Session userId 和 ACTIVE。撤销记录仍保留在 entitlement_grants，并通过订单列表和详情展示，交易历史没有被删除。每次 Release、Manifest 和未来下载都重新检查 Grant。

### 问：为什么先查 Grant，再查 Release？

答：

> grantId 来自浏览器，Service 先按 grantId、当前 userId 和 ACTIVE 状态查询。通过后才使用 Grant 中可信的 packageId 查询该套餐的 PUBLISHED Release，前端无法提交另一个 packageId 扩大范围。

### 问：怎样防止 Basic 用户读取 Pro 文件清单？

答：

> Manifest Service 先验证当前用户的 ACTIVE Grant，再把 Grant 的 packageId 与 releaseId 一起传给 SQL。查询要求 Release 同时匹配 id、Package 和 PUBLISHED 状态。跨套餐请求得到 404，且不会继续查询条目。

### 问：Release、Manifest 和 FileObject 为什么分开？

答：

> Release 表达套餐的一次正式版本，Manifest 表达该版本冻结的完整交付快照，ManifestItem 表达有序文件角色，FileObject 表达可复用的物理文件身份和摘要。分层后可以保留历史版本、复用相同文件，并避免存储地址进入业务模型。

### 问：为什么 API 不返回 storage_key？

答：

> storage_key 是后端内部定位，暴露后会泄漏目录结构并把存储实现固定成外部契约。Manifest API 只返回可展示和校验的元数据；下载接口根据业务 ID 重新授权，再返回一次性票据，浏览器始终不提交 storage_key。

### 问：前端怎样避免旧请求覆盖新请求？

答：

> useKeyedLoader 每次加载先 abort 旧请求，并递增 sequence。响应写入前同时检查 AbortSignal 和请求序号，即使旧请求没有及时中止，迟到结果也不能覆盖当前 key 的数据。组件卸载时继续取消并使旧序号失效。

### 问：为什么收起再展开不重新请求？

答：

> 第一次展开用 v-if 挂载组件，之后 hasOpened 或 openedReleaseIds 保留已打开记录；收起改用 v-show 隐藏，组件实例和数据仍存在。真实浏览器验收确认重新展开没有新增请求。

### 问：现在能说完成文件下载了吗？

答：

> 当前完成了 Classpath 小文件的一次性受控下载：票据五分钟过期、只能成功消费一次，消费时重新检查 ACTIVE Grant 与 PUBLISHED Release，响应前校验大小和 SHA-256，并记录响应准备审计。生产对象存储、大文件流、断点续传、限流和完整失败审计仍未实现。

## 21. 两分钟讲解稿与当前边界

理解后按自己的语言表达：

> 支付事务创建 ACTIVE EntitlementGrant 后，内容库按当前 Session userId 和 ACTIVE 状态查询，并从订单项快照展示购买事实。展开版本和文件清单时，服务使用 Grant 中可信的 packageId 限制 PUBLISHED Release 与 Manifest。Manifest API 不返回 storage_key。点击下载后，前端先申请五分钟一次性票据；消费时服务锁定票据、重新授权、核对 FileObject 与真实文件的大小和 SHA-256，再标记 CONSUMED 并记录 FILE_RESPONSE_PREPARED。前端 keyed loader 继续负责清单异步竞争，下载操作另有忙碌、成功和错误状态。当前非容器基线为 86 项后端测试，并做过真实 MySQL、文件保存、重复消费 404 和浏览器无障碍验收；另有 2 项 Testcontainers 测试因 Docker 不可用而跳过。
