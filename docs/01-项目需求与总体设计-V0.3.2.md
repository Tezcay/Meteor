# 多商家数字商品平台：项目需求与总体设计 V0.3.2

日期：2026-09-18  
状态：修订设计草案；不是已实现系统、导师批准或正式开工声明。  
配套：[核心业务设计](03-核心业务设计-V0.3.0.md)、[评价取舍与版本记录](04-评价取舍与版本记录-V0.3.0.md)。

## 1. 定位与设计目标

面向以文件形式交付的数字商品的多商家平台。商家发布并持续更新内容；买家浏览、购买，在个人内容库中获取自己有权访问的正式交付文件；平台管理入驻、发布审核与异常处理。

主要工程问题：购买成功后，正确用户持续获得正确版本的内容；重复事件、处理失败、退款与更新不会破坏订单—权益—文件关系。

开发目标同时包含好用、精致的用户端和可靠的后端业务，不以商城模块数量、算法名词或中间件数量衡量质量。普通商品浏览、订单等基础能力可以复用成熟模式，无需为避免“换皮”刻意重新发明。

用于专业实习课程，保留本科毕设拓展空间。二者可分离，同学课程题目获批不是本项目毕设通过的保证。不承诺创新性、真实商业需求或高并发规模。

## 2. 角色与产品范围

| 角色 | 能力 | 限制 |
| --- | --- | --- |
| 访客 | 浏览商品、店铺和公开展示素材 | 无正式交付文件访问权 |
| 买家 | 购买、内容库、下载、申请退款 | 仅访问自己的订单、权益 |
| 商家 | 入驻、店铺、商品与版本、查看本店订单 | 所有接口服务端限定店铺范围 |
| 管理员 | 入驻与发布审核、退款处理、异常处置 | 有权限校验与操作记录 |

本轮设计默认：账号可兼任买家与商家，每个商家账号一个店铺；不做店铺员工。多商家是完整首版范围，分阶段实现不等于删除。

平台面向“以文件形式交付”的数字商品，核心交易与交付模型不依赖单一商品类别或单一文件格式。首版选取少量代表性类别验证模型，不追求覆盖所有数字内容形态。

首批代表性类别：

- 模板：文档、表格、演示文稿、笔记／日记、可打印模板。
- 设计素材：图标、插画、界面素材、海报与视觉资源包。
- 摄影：单张摄影作品、照片合集或主题素材包。
- 出版内容：电子书、漫画、指南、教程文档。
- 数据与资源可作为后续样例：CSV／JSON／XLSX 等数据文件、参考资料包。

商品类别与文件格式分离。一个商品的一个版本可以同时交付多个文件，例如 PPTX + PDF + ZIP，或 JPG + PDF License。文件扩展名只描述交付载体，不直接决定商品业务类型。

常见首版交付格式可包括：

- 文档与表格：PDF、DOCX、XLSX、CSV、TXT。
- 图片与矢量：JPG／JPEG、PNG、SVG。
- 演示与出版：PPTX、PDF、EPUB。
- 资源包：ZIP。
- 其他格式只在实际样例需要时加入，不为“支持更多格式”提前增加解析能力。

不纳入首版：真实分账提现、多币种、跨店合并付款、复杂营销叠加、秒杀、积分、会员订阅、软件激活、DRM、直播、多清晰度转码、完整聊天、原生 App、开放社区、商家经营大屏及自由店铺装修。

首版也不提供“所有正式文件都可在线打开”的通用预览能力，不实现 Office 在线编辑／预览、PSD 解析、ZIP 在线浏览、电子书阅读器或视频流媒体等与核心交易交付无关的重型功能。

## 3. 交付分层与验收门槛

不再把全部功能标为同一个 P0。使用 C1、C2、E 三层，区分第一个可运行成果与完整第一版。时间需在得知课程截止日期和投入后估算。

### C1：最小可靠交易链路

- 登录与基础角色、店铺数据隔离。
- 简单商品列表、详情与套餐；预置测试商家、店铺和首个已发布版本。
- 一个订单项的立即购买、订单快照、独立的测试支付适配器与结果事件。
- 支付结果与权益在本地事务内应用，唯一约束和幂等从开始就做。
- 内容库、文件访问校验、短时下载授权与授权记录。
- 基础持久化记录、失败回滚／重试、支付结果核对入口。
- 最少两个商家与两个买家用于验证隔离；第一个演示可只操作一个店铺。
- 至少使用两种不同商品类别或两种不同交付格式，验证交易与交付模型未绑定单一文件类型。

C1 出口：一个真实可用样例从下单到授权下载走通；重复结果与事务中断测试通过；未购买用户和其他店铺账号无法越权。预置商品不算已经实现商家审核。

### C2：完整首版的发布与售后闭环

- 商家申请与平台审核、店铺公开页。
- 商品修订与套餐文件版本的提交、审核、发布、下架／禁用。
- 新旧版本访问、更新权益，禁止原地覆盖已发布文件。
- 整单测试退款、结果核对与按来源撤权。
- 商品普通下架和紧急文件禁用的区别处理。
- 失败任务管理、站内结果通知、管理操作审计。
- 有限分类搜索、用户页面与管理端的完整状态和部署验证。
- 商品展示素材与正式交付文件分开管理，公开资源和私有资源访问边界明确。

C2 出口：发布—购买—更新—退款／下架流程通过；跨商家隔离、旧订单不被当前商品修改、多来源权益等场景通过。C1 完成不能对外称 C2 已完成。

### E：按剩余时间选择

收藏、简单单券优惠、基础订单统计、AI 上架草稿辅助。大版本付费升级可作为后续毕设选做项。未完成这些功能不影响 C2 核心成立。

针对特定商品类型的增强能力，如图片 EXIF 非敏感信息提取、字体试用、音频试听、视频试看或 Web 模板 Live Demo，也只作为后续扩展，不属于首版通用能力。

## 4. 核心业务规则

以下为本轮采用的设计默认值，便于后续原型和实现；由助手依用户“做好取舍并迭代”授权提出，不冒充用户已逐项确认。

### 4.1 商品信息与交付内容

- Product 是稳定商品身份；ProductRevision 是标题、描述、分类、公开展示素材等商品信息的修订。
- 商品分类表示“用户购买的内容类型”，文件格式表示“内容如何交付”，两者不等价。
- Package 是稳定售卖套餐身份；价格和展示描述可更新，下单时保留快照。
- Release 是某一个 Package 的文件发布版本；首版不设跨套餐的全商品版本矩阵。
- Basic 和 Pro 分别发布自己的 1.0、1.1；Pro 可复用相同文件对象，但必须有明确交付清单，不自动继承 Basic。
- Release 的交付清单 Manifest 是该版本文件的完整集合，而非相对上版的增量。
- 一个 Manifest 可以包含多个文件和多种格式；业务逻辑不应写成“一个商品对应一个文件”。
- 用户界面显示套餐名、版本标签、更新时间和更新说明；内部用唯一 ID 与发布顺序识别，不依赖版本字符串大小比较。
- 商家改变商品标题、描述或展示素材不产生正式交付文件版本；增加／替换交付文件必须发布新 Release。
- 已发布修订与清单保持不可变；状态可以变为禁用，正式交付文件内容不可原地替换。

### 4.2 买家购买的是什么

首版购买的是指定套餐的持续访问资格，不是固定文件列表。策略名 `ALL_RELEASES`：可访问该套餐全部已发布且未禁用的历史版本，以及将来满足条件的新版本。这个策略按订单快照与权益来源记录保存，不因当前商品说明变化而改写。

例：在 Basic 1.0 购买，Basic 1.1 新增文件可获得；Pro 1.1 的文件不能因此获得。若 Basic 1.1 移除一个文件，旧 Basic 1.0 清单仍保留，只要未被禁用就可访问。

套餐停止销售不撤销旧资格；“包含未来更新”表示有更新发布时可获得，不承诺永久提供更新或平台永久运营。首版不支持把已有套餐偷偷改成全新商品，重大重新售卖使用新套餐或新商品身份。

### 4.3 权益按来源记录

- 每个有效支付订单项产生一条 EntitlementGrant，唯一来源为订单项。
- 记录用户、套餐、来源、策略快照、状态、发放时间与撤销原因，不用 user_product.has_access 布尔值代替。
- 判定访问：存在至少一条满足请求版本策略的有效 grant，且版本已发布、文件未禁用、清单确实包含所请求文件。
- 退款只撤销该订单来源的 grant；其他有效来源不受影响。
- 正常界面提示已拥有并引导内容库；服务端拦截明显重复购买。但并发订单、历史数据等仍按来源设计，不依赖前端防重复。

### 4.4 订单与测试支付

- 立即购买，一笔订单一个套餐，人民币，正金额测试购买；零元领取另行设计，不伪装成支付成功。
- 保存商品、店铺、套餐、数量、金额、币种、使用范围、权益策略快照，卖家操作不可回写。
- 定价与结账由服务端核对；金额用精确类型。创建订单保存当时允许售卖的规则和有效期。
- 测试支付通过独立逻辑适配器持久化支付结果并投递事件，不是前端按钮直接置订单已付；可以与主应用同进程，无需另建微服务。
- 回调验证身份、事件关联、交易号、金额与币种；同事件幂等之外，还需保证同一交易和订单项不会重复应用。
- 订单关闭后的晚到成功记录为真实测试支付成功，但订单不重新打开、不发权益，产生核对／退款处理记录。
- C1 允许管理员通过受控入口完成测试款退回并留痕；C2 通过统一退款流程完成。异常资金结果不能靠“忽略”或“关闭提醒”消失。

### 4.5 展示素材、退款、下架与文件访问

- 商品公开展示资源与正式交付资源分离。PreviewMedia 用于封面、效果图、样例页、局部展示图及可选的简短演示视频；ReleaseFile 属于正式交付内容。
- PreviewMedia 可公开访问，但不能与正式交付文件共用需要权益控制的私有访问路径。
- 首版不把 ReleaseFile 直接作为未购买用户的在线预览来源，也不因浏览器“能打开某格式”就默认公开正式文件。
- 摄影类商品的正式原图可保留原始元数据并在购买后交付；公开展示图应视为独立资源。首版不要求解析 EXIF，也不公开展示 GPS 等可能涉及隐私的敏感元数据。后续如提取 EXIF，只展示明确允许的非敏感字段。
- C2 首版整单退款，买家申请，管理员审核，商家只查看本店处理结果；同一交易至多一笔活动退款申请。
- 待审核、处理中、已知失败期间不默认撤权；退款成功结果与来源撤权在本地事务内一起应用。
- 已知失败可重试；超时或未知结果先核对，不直接另开一笔退款。
- 普通商品下架／店铺暂停：停止新单，不删除旧订单和资格；有效旧单可继续交付。停用后的历史售后由管理员处理。
- 文件安全或侵权处置：单独禁用具体文件或版本，立即阻止签发新的下载授权，说明不可用状态并支持售后。
- 正式文件私有。首版签发短时 URL，授权日志记录“签发或拒绝”，不是“客户端下载成功”。不记录完整签名 URL／密钥。
- 已签发 URL 在有效期内可能继续可用，撤权不承诺即时召回凭证或已下载文件；需要即时阻断时另做对象层禁用或代理方案。

## 5. 界面与交互基线

用户端：发现、分类／搜索、店铺、商品详情、结账结果、内容库、订单详情。商家端：入驻、商品与文件版本、审核状态、本店订单。管理端：审核、退款、异常处理与操作记录。三种角色视图不要求三个独立前端工程。

视觉坚持：柔和配色、统一展示比例、清晰留白；商品效果与实际交付内容一致；不堆促销标记和大屏。不能为了后端主题把用户界面变成事务日志展示。

商品详情页不承担正式文件在线阅读／编辑功能。购买前通过独立的商品展示素材、文字描述、套餐说明、格式与规格信息、交付内容摘要帮助用户判断商品；购买并获得有效权益后，正式文件进入内容库并按权限下载。

建议公开展示的信息包括：商品类别、套餐、当前版本、更新时间、主要文件格式、文件数量或总大小、尺寸／页数等适用规格、授权说明、更新规则。真实私有存储地址、签名 URL 和不必要的内部文件信息不得公开。

| 关键页面 | 必须能表达的状态 |
| --- | --- |
| 商品详情 | 展示素材、套餐所含内容、主要格式／规格、当前版本、更新规则、已拥有、暂停销售 |
| 购买结果 | 待支付、支付结果核对中、可获取内容、关闭后付款待处理 |
| 内容库 | 可访问版本、新版本、正式文件列表、因退款无资格、因文件禁用不可用 |
| 商家发布 | 商品信息与展示素材、草稿、待审核、驳回理由、已发布、发布失败且未覆盖旧版 |

先完成三个核心原型：商品详情、内容库、商家发布；再补发现和审核页面。组件和视觉参考统一，不整页混拼竞品。

## 6. 技术基线

- Vue 3 + TypeScript + Vite；2026-09-20 根据学习成本与现有工程确认继续使用 Vue。首页采用独立组件与原生 CSS，不强制引入 Tailwind CSS。组件库不作为前提，是否引入在核心原型验证后决定。
- Java 21 + Spring Boot 模块化单体，角色权限在服务端统一校验。
- 前后端分离，通过 REST API + JSON 通信；前端不承担订单金额、权限、支付状态、权益等最终业务判定，关键规则均由后端校验。
- 默认数据库调整为 MySQL（InnoDB）。全新环境建议优先核验 8.4 LTS；若现有课程、虚拟机或工具已经稳定使用 MySQL 8.0，可以继续使用并固定具体版本，不为版本号重装环境。依据是用户已明确 Java 后端秋招目标与课程衔接需求，且尚无实现或迁移成本；PostgreSQL 仍能胜任，但本项目不再并行学习两套数据库。索引、隔离级别、锁及约束设计按实际选定的 MySQL 版本测试。
- 对象存储区分公开展示资源与私有交付资源。PreviewMedia 允许公开读取；ReleaseFile 保持私有。上传对象使用新 key，不覆盖已发布文件。
- 本地事务优先；需异步执行的通知／核对以持久化任务记录管理，首版不强制 MQ、微服务。Redis 纳入求职学习和项目增强计划，首先验证公开商品展示缓存；不缓存下载授权结论，不以 Redis 代替数据库中的订单、权益、业务唯一约束和恢复记录。C1 核心验收不依赖缓存完成。
- 开发可在 Windows IDE 进行；用户自己的 Linux 虚拟机用于命令、服务部署和排错学习。Docker Compose 与 Nginx 纳入交付实践，按阶段引入，不要求第一天搭齐。
- 测试支付结果与业务应用之间的边界、任务恢复、唯一约束见配套设计。具体依赖版本与存储服务实现前核验。
- 上传中、可用、被版本引用、待清理文件分开处理；清理前再次检查引用，不能删除正在发布的对象。应用不执行上传内容。
- 首版不引入通用文件解析／转码服务。若后续为摄影、字体、音视频等类别增加专属处理能力，应作为独立增强模块，不改变交易、权益与版本交付主链路。

## 7. 数据与验收

C1 只需要少量真实文件和不同身份的测试账号。样例应至少跨两种商品类别或交付格式，验证底层模型不是为单一模板类型硬编码。

C2 建议约 12—20 个商品、少量测试店铺，至少 3 个含不同套餐或版本；可覆盖模板、设计素材、摄影、出版内容中的若干类别，但不作为硬性数量指标。

自制或获准再分发的文件保留来源与许可。公开能看见竞品页面不等于可以搬运其付费商品或图片。测试价格、订单和性能样本明确标注，不伪造经营数据。

| 验收编号 | 场景 | 预期 | 阶段 |
| --- | --- | --- | --- |
| A01 | 未购买／跨账号下载，跨店访问订单 | 服务端拒绝且不泄漏私有地址或其他店数据；公开展示素材仍可正常访问 | C1 |
| A02 | 同一回调重复 10 次，同交易不同事件 ID | 支付与 grant 各一次有效应用，通知不重复创建 | C1 |
| A03 | 支付结果已在适配器成功，业务事务中间崩溃 | 业务回滚，重新投递／核对后恢复；无半条权益 | C1 |
| A04 | 事务提交后应答丢失 | 重复回调返回既有结果，不重复发放 | C1 |
| A05 | 错金额、错币种、伪回调、错交易关联 | 不置已付、不发权益，记录必要诊断信息 | C1 |
| A06 | 订单关闭与付款成功并发 | 按事务串行结果应用；晚到付款记账并待退，不静默丢失 | C1/C2 |
| A07 | Basic 购买后发布 Basic 新版与 Pro 新版 | Basic 更新可访问，Pro 不可访问 | C2 |
| A08 | 文件未就绪发布／试图覆盖已发布内容 | 阻止发布或要求新版本，旧记录稳定 | C2 |
| A09 | 两笔有效来源之一退款 | 只撤销对应 grant，另一个仍有效 | C2 |
| A10 | 退款成功后重放原支付成功 | 不恢复已撤销 grant、不把退款订单改回已付 | C2 |
| A11 | 退款未知、重复请求或晚到结果 | 保持核对，不重复退款；成功后原子撤权 | C2 |
| A12 | 普通下架与紧急禁用 | 分别停止新购或新授权；已签 URL 窗口明确 | C2 |
| A13 | 后台任务崩溃后恢复／重复领取 | 可重新领取；副作用幂等或明确重复风险 | C1/C2 |
| A14 | 用户没有真正下载完整文件 | 只展示授权记录，不统计为已完成下载 | C1 |
| A15 | 同一 Release 含多种格式文件 | Manifest 与授权按文件正确工作，不因扩展名改变权益规则 | C1/C2 |
| A16 | 未购买用户访问商品页 | 可查看公开展示素材和规格，但无法获得正式 ReleaseFile 或其私有地址 | C1/C2 |

所有验收项目前均为待实现、待测试。压测记录环境、数据量、延迟与错误率，不宣称真实运营规模。AI 选做项单独评估内容准确性，不代替上述验证。

## 8. 后续工作与毕设

顺序：确认本轮业务默认值 → 核心原型与少量跨类别样例 → C1 验证 → C2 → 选择性拓展。数据库具体表结构、API 与代码须在原型和关键验证后细化，当前模型不是完整 DDL。

工作题目保持为：《数字商品交易与版本交付平台的设计与实现》。平台可承载多类数字文件商品，但不以“什么都能卖”作为创新点；核心仍是交易一致性、版本交付、权益控制与故障恢复。

毕设深化仍为：交易一致性、版本交付、权限与故障恢复的设计及验证。多商家完整产品并未删除，但不以经营大屏、营销中心或大量文件处理功能作为核心成果。
