# 决策记录与下一步

日期：2026-09-15  
关联文档：[项目需求与总体设计 V0.1](01-项目需求与总体设计-V0.1.md)

## 已从讨论中明确的方向

- 当前是专业实习课程项目，期望后续可拓展为本科毕设，二者可分离。
- 当前重点候选是多商家数字商品交易与交付平台，用户希望先记录和设计，尚未授权开始实现。
- 接受成熟产品参考，不追求市场空白或高深算法。
- 需要漂亮、简洁、有完整使用过程的 Web 产品；喜欢好看界面不等于想做艺术创作工具。
- 需要有实际后端业务与技术深度，避免普通商城仅替换图片和商品类别。
- 商家入驻可纳入设计，不因其存在就默认必须真实分账。
- 多币种没有必要。简单优惠券可以考虑，复杂营销不作默认需求。
- 数字文件下载与完整视频流媒体服务应区分。
- 双人共同目标与日程协调仍作为备选，未被否定；本次不继续扩展该方案。

## V0.1 提出的默认值，尚未确认

| 决策点 | 建议默认值 | 选择理由 |
| --- | --- | --- |
| 商品范围 | 模板与视觉素材 | 预览与文件交付方式相对统一 |
| 店铺关系 | 一个商家账号一个店铺 | 避免员工组织与复杂授权 |
| 结账 | 单商品、单套餐立即购买 | 先做完整可靠链路，避免跨店拆单 |
| 支付 | 服务端测试支付适配器 | 不依赖商户资质与真实资金 |
| 更新权益 | 购买套餐包含其后续更新 | 规则简单，可逐步拓展 |
| 退款 | 整单测试退款 | 避免部分退款与优惠分摊 |
| 发布审核 | 商品与新版本均审核 | 对齐多商家平台的管理角色 |
| 技术栈 | Vue 3、TypeScript、Spring Boot、关系数据库、对象存储 | 利用已有 Java 经验，保持架构简单 |
| AI | 可选上架辅助 | 不阻塞交易与交付 |

默认值是方案建议，不得在后续对话中当作用户已经确认的要求。

## 开发前必须弄清的限制

1. 课程提交截止时间、每周可投入时间、是否组队。
2. 学校是否有需求书、设计书、开题报告的指定模板。
3. 演示部署方式、设备和网络条件，以及可接受成本。
4. 至少几个真实可用商品样例及其再分发许可。
5. 测试支付是否满足课程演示要求；是否需要真实支付接入。

这些问题不阻止现在做原型，但应在估算开发计划前明确。

## 下一步顺序

### 第一步：审阅需求草案

核对定位、范围、角色和默认业务规则。优先修正业务含义，不先纠结技术组件。

### 第二步：核心流程与低保真原型

先做三个可审阅成果：

- 商品详情：套餐、包含内容、版本和购买说明是否清楚。
- 我的内容库：购买后怎样下载、查看旧版本和获得更新。
- 商家发布流程：文件、预览、版本、审核如何衔接。

随后统一视觉风格，再补发现页、店铺页和管理端。未经用户要求不直接套用整站生成工具开工。

### 第三步：最小技术验证

使用一份真实文件、一个测试商品和两个账号，验证私有存储、测试购买、权益判断和下载。验证重复事件与中途失败。此阶段再确定存储、支付适配器和依赖选择。

### 第四步：详细设计

在前面规则稳定后补充：

- 数据库 ER 图、表结构与约束；
- 订单、发布、退款状态图；
- 支付确认与交付时序图；
- 接口契约、权限矩阵与错误码；
- 测试场景、开发里程碑和部署说明。

不提前为几十张表、上百个接口写形式化文档，也不把数据库和 API 与未定规则绑定。

## 文档使用方式

- V0.1 是需求与总体设计合并草案，适合当前选题阶段。
- 业务变化先更新主文档，再记录重要决策；不要不断新增互相矛盾的方案副本。
- 学校需要正式 Word 或开题格式时，再按模板整理，保留“课程项目”和“毕设拓展”的区别。
- 未进行代码实现、支付接入或真实商品数据收集。文档中的验收项是计划，不是已通过的测试结果。
