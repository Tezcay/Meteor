# Meteor：项目需求与总体设计 V0.4.0

日期：2026-09-26  
状态：**当前有效、暂时稳定的产品与工程基线**。本文替代 V0.3.x 作为需求入口；旧文档保留为决策历史，不再并行修改。配套：[核心业务设计 V0.4.0](03-核心业务设计-V0.4.0.md)、[版本记录 V0.4.0](04-评价取舍与版本记录-V0.4.0.md)。

## 1. 产品定位

Meteor 是面向创作者的数字作品发现、发布与授权交易平台。它服务于摄影、插画、设计素材、模板、字体、3D 素材、音频与电子出版物等**以文件交付**的创意内容。

产品不以“商品越多越好”或“AI 推荐越多越好”为目标。其价值由三件事构成：

1. 浏览者能从作品、系列和创作者脉络中发现内容，而不是陷入无限重复的商品墙；
2. 创作者可以把一份包含多张作品或多种文件的内容，清楚地发布、更新和交付；
3. 购买、版本更新、退款与下载授权保持可靠、可解释、可追溯。

首版是模块化单体 Web 应用，不承诺真实商业规模、真实支付或高并发。课程演示与未来毕设扩展分开评估。

## 2. 用户与角色

账号可同时具有买家与商家身份；角色不是孤立的前端皮肤，服务端必须做最终校验。

| 角色 | 可做什么 | 不可做什么 |
| --- | --- | --- |
| 访客 | 浏览公开作品、系列、店铺、展示素材与评分摘要 | 访问正式交付文件、下单、给出已购评分 |
| 普通用户／买家 | 下单、管理订单与内容库、下载已获授权文件、申请退款、为已购商品评分 | 访问他人订单、权益或私有文件；修改作品 |
| 店家／创作者 | 申请入驻、管理自己的店铺、商品、系列、版本与本店订单 | 绕过审核发布；查看其他店数据；处理退款结论 |
| 管理员 | 审核入驻和发布、处理退款与异常、维护平台分类体系、留存操作记录 | 修改已发布版本内容来伪造历史；绕过审计 |

前端可以用本地演示角色帮助展示流程，但登录态、角色、店铺归属、价格、支付结果、权益和下载许可都不能由前端作最终判定。

## 3. 内容模型：商品、系列、作品与文件

### 3.1 必须区分的对象

| 对象 | 解决的问题 | 例子 |
| --- | --- | --- |
| 商品 Product | 交易和授权的稳定对象 | “冬日静谧：6 张插画海报包” |
| 系列 Collection | 面向浏览的策展关系，不直接等于订单 | “Winter stillness”六张同主题海报 |
| 作品 Asset | 系列或商品中可展示的单件内容 | 其中一张雪林海报或一幅摄影作品 |
| 套餐 Package | 买到哪一档内容与使用范围 | 标准包、完整包、商用扩展包 |
| 发布版本 Release | 某套餐的不可变交付清单 | 完整包 v1.1，含 6 张 PNG 与授权 PDF |
| 公开展示素材 PreviewMedia | 购买前可看的封面、局部、效果图 | 压缩后的封面与预览图 |
| 正式交付文件 ReleaseFile | 购买后受权限保护的文件 | 原图、ZIP、PSD、字体包、PDF |

一个插画商品可以有一张主封面、多个预览图和多份交付文件；一个摄影商品也可以是单幅、主题合集或素材包。页面不能默认“一份商品只含一张图”。

### 3.2 分类、标签与小类

分类用于导航、筛选和归档，不用于替代创作者的表达：

- **一级分类**：设计素材、实用模板、摄影、插画、字体、3D 素材、音频、电子书。
- **平台维护的小类**：例如摄影下的“建筑／自然／人物／静物／空间”，插画下的“风景／角色／编辑插画／海报”。它们是受控词表，可演进但不可由任意用户随意新建。
- **创作者填写的标签**：如“冬日、蓝调、静谧、可打印、日落”。用于检索与相关推荐，允许多选。
- **系列关系**：由创作者创建、平台审核或运营精选建立，必须有明确标题、封面和排序；不要凭图片相似度自动把内容拼成一行。

首版不依赖 AI/Agent/知识库来决定分类。后续可让 AI 根据标题、描述和预览图提出“小类与标签建议”，创作者确认后再写入；人工审核可纠正。AI 不能自动发布、自动合并系列、决定授权或影响搜索排序的公平性。

## 4. 发现与浏览体验

### 4.1 首页与发现页分工

首页是编辑式入口，不承担完整目录：保留现有的“精选海报叠放”作为唯一强记忆点，展示有限的精选主题和进入发现页的路径。它不应堆成巨型页面，也不应让下一段内容只露出一小截而抢走首屏焦点。

发现页是可扩展目录，按以下顺序组织：

1. 紧凑的分类入口与可展开搜索；
2. 少量人工策展的系列（每个系列说明主题与作品数量）；
3. 可分页或无限加载的完整目录；
4. 分类、小类、标签、价格／授权、排序等筛选，不以每个大类横向一行的静态轮播承载无限作品。

系列页展示同一主题中的多件作品，并能向下继续浏览。商品详情则解释具体套餐、文件、版本、授权和购买；点击任意卡片不应无提示跳到一个无关联的页面。

### 4.2 目录与卡片规则

- 标准目录使用稳定列宽、不同内容高度的自适应网格；图片使用 `object-fit: cover` 的展示裁切只限缩略图，详情或系列中必须提供完整比例的查看方式。
- 同一列的垂直间距与列间距保持接近，首行先对齐；不为了“瀑布感”在开场做突兀错位。
- 大量作品时使用分页或连续加载，并保留 URL 中的分类、筛选、排序和页码／游标状态。
- 横向滑轨只用于少量、有明确主题的策展集合，支持鼠标滚轮、触控拖拽、键盘和左右按钮；不露出浏览器原生横向滚动条。
- 卡片悬停只反馈可点击性、焦点与少量元信息，不让每张卡片旋转、浮起或自动播放。

### 4.3 搜索与排序

默认导航只显示搜索图标；点击或键盘聚焦后平滑展开为短搜索框／搜索面板。搜索面板承载关键词、分类快捷选择和结果，避免页面顶部与正文重复出现同一长输入框。

完整目录的首版排序为“推荐、最新、评分最高”；筛选为一级分类、小类、标签、价格／授权范围。先让每个筛选都有稳定字段与 URL 表达，再考虑个性化推荐。

## 5. 商品详情、评分与购买

### 5.1 商品详情

详情页以完整作品预览或系列预览为中心，购买区在桌面端与预览相邻、在小屏幕改为预览之后。必须清楚呈现：

- 商品／系列关系、作品数量与预览内容；
- 套餐差异、价格、授权范围、文件格式、文件数量／大小与必要规格；
- 当前版本、更新时间、更新说明和“未来更新”的实际含义；
- 已拥有、停售、审核中／不可用等状态；
- 评分摘要与评分入口。

正式文件不作为未购买预览。摄影原图和可能含敏感 EXIF 的文件仅在购买后交付；公开预览使用独立资源。

### 5.2 评分，不急于开放评论

首版加入商品评分，不做开放式评论区：

- 只有拥有有效权益的用户可以对已购商品提交 1—5 星评分；每个用户每个商品一条，可修改，聚合值随之重算。
- 商品页显示平均分、评分人数和分布摘要；评分样本不足时显示“评分较少”，不制造精确幻觉。
- 退款或资格撤销后，历史评分是否保留由产品策略决定；首版建议保留但标记为“已购时评分”，不允许再次修改。
- 文字评价、回复、举报和内容治理不是 C1/C2 的隐性工作量，后续单独立项。

### 5.3 购买与内容库

购买流程为：选择套餐 → 服务端创建订单与测试支付尝试 → 等待可靠支付结果 → 生成来源权益 → 进入内容库。前端按钮不可以直接把订单写成已支付。

内容库是“我拥有什么、能拿到什么版本”的工作台，不是大标题加空白墙。已购状态优先显示作品、所购套餐、最新可用版本、更新与下载；空状态应紧凑、明确，并提供发现入口。

## 6. 发布、审核与角色工作台

创作者发布流程分为：商品信息 → 分类、小类、标签与系列 → 公开展示素材 → 套餐 → 交付清单 → 版本说明 → 提交审核。发布页必须同时说明“审核中的新版本不会覆盖当前线上版本”。

管理员维护分类词表、审核商家与发布、处理退款与异常；创作者只看到自己店铺的业务数据。审核记录、退款处理和权限拒绝必须留痕。

## 7. 视觉与交互基线

界面气质是**安静的创作目录**：让用户提供的作品主导颜色和情绪，界面用暖白、石灰、墨色和克制的梅紫状态色承托，而不是把每页做成独立海报。

- 不用手写／书法字体作为系统标题；以清晰的中文无衬线为主，作品图片内的字体属于作品本身。
- 保持紧凑而有呼吸的垂直节奏；避免巨型标题、首屏以下只露出半张无关卡片、内容库的空旷留白。
- 首页海报叠放可有一次轻量的入场与轮播位移；其余动效优先回应用户操作：搜索展开、按钮微缩回弹、卡片聚焦、列表分批出现。
- 尊重 `prefers-reduced-motion`，所有可点击元素都需要 hover、focus、active 三种可感知反馈。
- 深色模式不是把浅色值反相：后续单独建立语义色 token、预览背景和边界层级，再做逐页验证。
- 移动端不保留依赖横向浏览器滚动条的核心操作；复杂发布和订单详情走独立页面而非大弹窗。

## 8. 后端与接口边界

前端布局重做不改变交易核心；稳定字段和接口契约才是前后端之间的边界。建议按资源组织：

| 能力 | 首要接口／数据 |
| --- | --- |
| 目录 | `GET /products`：category、subcategory、tag、sort、cursor/page；返回商品卡片与评分摘要 |
| 系列 | `GET /collections`、`GET /collections/{slug}`：策展信息、排序后的作品卡片、下一页 |
| 商品 | `GET /products/{id}`：预览、套餐、版本摘要、规格、评分摘要、已拥有状态 |
| 评分 | `GET /products/{id}/ratings`、`PUT /products/{id}/rating`；服务端验证有效权益 |
| 结账 | 创建订单、创建／复用支付尝试、查询结果；金额与资格均由服务端计算 |
| 内容库 | `GET /library`、版本／文件列表、受控下载授权；不返回私有存储地址 |
| 创作者 | 商品草稿、展示素材、套餐、Release、审核状态；服务端检查店铺归属 |
| 管理端 | 审核、退款、异常与分类词表；每次变更保留操作人和时间 |

本地模拟数据层可继续用于前端演示，随后逐接口替换为 API。接口接入不会要求把已稳定的页面视觉推倒重来；变化集中在数据获取、加载／错误状态和权限来源。

## 9. 交付范围与顺序

### C1：最小可靠链路

- 登录、角色与店铺数据隔离；
- 跨至少两类文件的商品目录、详情、套餐和预览；
- 单订单项的测试支付、幂等结果处理、权益发放；
- 内容库、私有文件授权、下载记录；
- 分类／小类／标签的基本筛选；
- 访客、买家、创作者、管理员的服务端权限验证。

### C2：完整首版闭环

- 入驻与发布审核、草稿／审核／发布／禁用生命周期；
- 套餐 Release 更新、历史版本与不可变交付清单；
- 退款、核对、按来源撤权、异常处理与审计；
- 系列页、可扩展完整目录、紧凑搜索和排序；
- 已购评分；
- 部署、故障恢复、关键权限与并发场景验证。

### 明确不进入当前版本

真实分账提现、多币种、跨店购物车、会员订阅、秒杀／积分、DRM、在线编辑／全格式在线预览、流媒体、自由店铺装修、开放社区、开放评论、复杂个性化推荐、通用 AI 自动审核或自动分类。

## 10. 验收要点与未决项

除 V0.3 的支付、退款、授权、版本不可变与跨店隔离验证外，V0.4 额外验证：

| 场景 | 预期 |
| --- | --- |
| 插画／摄影合集 | 一个商品可展示多件作品，购买后按套餐获得完整交付清单 |
| 目录扩容 | 同一分类可加载多页；筛选与排序可复现，不靠一条横向轨道承载全部内容 |
| 系列关联 | 系列中的排序来自明确的策展数据，不因图片“看起来相似”自动拼接 |
| 评分 | 无有效权益不能评分；重复评分更新同一条记录；商品只收到聚合摘要 |
| 角色越权 | 前端入口隐藏不是安全边界；服务端拒绝跨用户、跨店、跨角色请求 |
| 视觉节奏 | 主要页面在常见桌面和移动宽度下不出现巨型空白、被裁断的主操作或浏览器横向滚动条 |

尚未确认的事项：课程截止日期、真实支付是否需要、对象存储和部署成本、最初的获授权商品／文件来源。它们影响排期，不推翻上述产品模型。
