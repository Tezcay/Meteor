# Meteor：面向 Java 后端秋招的一月冲刺学习计划

日期：2026-09-16。依据用户已补充的学习经历制定；Day 1 从实际开始那天计，不绑定固定日历。配套：[知识大纲与资料](06-技术知识地图与项目学习路线.md)、[项目评估](05-项目评估与学习实施建议.md)。本轮只写计划，不开始实现。

## 1. 适合你的目标与节奏

你不是完全零基础：已经有面向对象、Spring／Spring Boot／MyBatis 和 SQL CRUD 的接触经验。主要缺口是语言基础的常用部分、数据库正确性、Web 安全与真实排错经验。先用小任务检验已有知识，不重新刷一遍完整 Java Web 视频课。

一个月的主目标：**做出并能解释测试购买到私有文件交付的正常闭环，完成 MySQL、Redis 和 Linux 的可验证实践，并争取覆盖 C1 的关键异常。** 完整 C1 是冲刺目标；不把全部 C2、真实支付、微服务或 AI 上架功能塞进这个月。

这是进取目标，不是完成保证：C1 包含恢复、隔离和并发，新增 Redis、Linux 与 MySQL 深化也会占用时间。月底分别记录“项目链路完成到哪”“MySQL／Redis／Linux 学到哪”“哪些 C1 场景已验证”，不把接触过的技术写成熟练掌握，也不临时降低可靠性标准。

一个月内不应只做项目。保留基础与算法、投递和复盘时间；不必等项目完全完成才开始关注岗位与投递。本计划不声称任何企业的具体招聘截止时间。

### 建议每日安排

先试三天，不承诺每天坐十小时。一天可留较大时间窗口，但初始只安排 **5—6 小时有效学习**，拆成专注块，中间正常休息。

| 内容 | 每个学习日的初始预算 | 做什么 |
| --- | --- | --- |
| 项目与专项基础 | 1.5 小时 | 当天会用到的集合、MySQL、Redis、Linux 或网络；读少量资料再实验 |
| 项目实践 | 2—2.5 小时 | 一条小功能或一个异常场景；包括调试和验证 |
| 算法与计算机基础 | 1—1.5 小时 | 数组、哈希表等；并发、网络、JVM 分小块补 |
| 复述与记录 | 0.5 小时 | 看 diff、记录根因、无 AI 讲解、安排下一步 |

每周按 6 个学习日 + 1 个休息／轻复盘日设计。一个月约 24 个完整学习日，合计约 120—144 小时有效时间。约 72—84 小时用于项目主链路，24—30 小时用于 MySQL／Redis／Linux 专项，24—30 小时用于算法与计算机基础；部分任务可以重合。完整 C1 原估算本就需要约 120—184 小时，新增专项后不能再把“一个月完成 C1”当作默认承诺。

如果连续三天完成后仍有余力，可额外加 0.5—1 小时到项目验证或当天薄弱知识，优先保证理解和休息。不要把新增时间全部用于观看视频。若当天状态差，只做 2—3 小时的一个小任务和复述，不用第二天加倍补债。

| 网络 | HTTP、Cookie／Session、CORS、HTTPS 基本作用、TCP 可靠传输和超时的基本认识 | Socket 实战、Netty；不是做 Web 项目的前置要求 |

## 2.1 技术深度如何判断

技术深度不按依赖数量计算。项目的主深度仍是事务、幂等、权限、版本权益和故障恢复；MySQL、Redis 与 Linux 提供岗位覆盖和实操证据。每项技术区分三层：

| 层级 | 含义 | 简历表达 |
| --- | --- | --- |
| 知道 | 能说用途和基本概念 | 通常不单独写成项目技术栈 |
| 做过实验 | 能复现行为、保留数据并解释限制 | 可写“实践／了解”，面试据实说明 |
| 项目使用 | 解决了明确问题，测过正常、失败与边界 | 可写具体场景、方案和验证结果 |

Redis 的合格项目使用是“公开商品缓存＋更新失效＋故障回源＋对照测试”，不是启动一个 Redis 容器。Linux 的合格实践是能从进程、端口、日志、配置和依赖定位一次部署故障，不是背命令表。MySQL 的合格实践是能用约束、事务、锁和执行计划解释真实 SQL，不是只背八股答案。

## 7. 如何让 AI 帮你加速，而不是替你跳过学习

核心路径第一次学习采用“自己先写规则／SQL／伪代码 → AI 只给提示 → 自己实现 → AI 审查 → 自己验证”。不要求第一次就不查资料写出框架所有配置。

可以较早交给 AI：依赖配置解释、简单页面样式、重复字段映射草稿、测试数据、文档整理。你必须看差异并能修改。应由你主导：权限判定、事务边界、唯一约束、支付状态转移、失败后应有什么结果。

如果时间紧，AI 可以提供核心实现参考，但该任务暂时标“借助 AI 跑通”，不能标“掌握”。第二天自己完成一个变式：例如把重复事件换成同交易不同事件 ID，或把查自己的订单改成查自己的文件版本；做不出来就缩小练习再学。

每天结束问自己三个问题：今天我能独立完成什么？我曾经以为正确但实验否定了什么？明天关掉 AI 后第一步怎么做？回答比代码行数和学习时长更能帮助调整节奏。

## 8. 每周调整规则

只记录实际专注分钟、完成的可验证任务、主要卡点，不记录“全天在电脑前”作为有效时间。D6、D13、D20、D27 对照出口检查一次。

如果主要卡在语法与概念，下周增加小练习，减少页面和功能；如果主要卡在环境，用 AI 集中解决环境并保留说明；如果能运行但解释不了，停止扩展，用一个变式测试掌握程度。连续两周未达到出口，不靠压缩睡眠追赶，重新估算目标。

这个月最划算的成果，是你能够亲自维护、解释和改动的一条可靠业务链路，以及一批被实验检验过的基础知识。完整的版本审核、退款 UI 和产品打磨，可以在之后按 M6—M7 延伸。

| 当前核心 | Java 常用基础、集合、异常、并发入门、Spring Boot／MyBatis、MySQL、Redis、Linux、HTTP、Git、Maven、测试、算法 | 一月计划必须覆盖，并留下实验或项目证据 |
| 紧随其后 | JVM 系统复习、并发包、RabbitMQ、Docker／Nginx 深化、设计模式 | 一月未覆盖完整的部分在下一个 4—6 周补；MQ 先选一种 |
| 岗位驱动 | Spring Cloud、Kafka／RocketMQ、Elasticsearch、Jenkins、Kubernetes、分库分表 | 收集目标岗位后按出现频率和项目需求选择；先做独立小实验，再决定是否进入 Meteor |

MongoDB、Dubbo、ZooKeeper、多个 MQ 和多个注册中心不需要同时学。一个掌握到“项目使用”层级的 Redis／MySQL／Linux 组合，比五个只看过视频的中间件更有说服力。之后若目标岗位普遍要求 Spring Cloud，可把商品浏览或通知做成独立练习服务；Meteor 主交易仍保持模块化单体，直到拆分有清楚的边界与验证目的。

每两周抽取本人准备投递的 10—15 个岗位做技能表：统计必需项、了解项、加分项，记录自己处于“知道／实验／项目使用”的哪一层。学习顺序以真实岗位频率和自己的薄弱点修正，不以课程目录长度制造完成感。
