# Meteor：项目代码语法与面试问答 V1.0

日期：2026-10-02
适用目标：零基础快速看懂自己项目中的代码，并能应对围绕简历项目的面试追问。

这不是 Java 或 TypeScript 语法大全。只解释 Meteor 当前真实使用的写法，并始终回答三个问题：

1. 这行代码在语法上是什么意思？
2. 它在 Meteor 的请求链路里承担什么职责？
3. 面试官为什么可能追问它？

## 1. 先建立项目全景

Meteor 当前完成了三条可以实际运行的核心链路：

```text
登录：Vue auth.ts
  → Spring Security
  → AuthController
  → DatabaseUserDetailsService
  → AccountMapper
  → users / user_roles

下单：Vue orders.ts
  → OrderController
  → OrderService
  → ProductMapper + OrderMapper
  → products / packages / orders / order_items

测试支付：Vue payments.ts
  → PaymentController
  → PaymentService
  → OrderMapper + PaymentMapper
  → orders / payment_attempts / payment_events
```

面试时不要从“我用了 Spring Boot”开始背。先说业务问题，再说技术怎么保护它：

> 用户登录后提交商品和套餐，服务端重新核价并保存订单快照；重复下单通过幂等键处理。支付成功事件在事务中校验金额、币种和订单状态，利用订单行锁与数据库唯一约束防止并发重复处理，最后把订单从 PENDING_PAYMENT 更新为 PAID。

这段话就是整个项目的技术主线。

## 2. Java 语法：只看项目中真正出现的

### 2.1 `package` 和 `import`

以 [OrderService.java](../backend/src/main/java/dev/meteor/order/service/OrderService.java) 为例：

```java
package dev.meteor.order.service;

import dev.meteor.order.mapper.OrderMapper;
import org.springframework.stereotype.Service;
```

- `package` 表示类所在的命名空间，也对应目录结构。
- `import` 让当前文件可以直接写 `OrderMapper`，不用每次写完整类名。
- `dev.meteor.order` 是业务模块；其下再分 `controller`、`service`、`mapper`、`dto`。

面试追问：为什么按业务模块分包，而不是把所有 Controller 放一起？

建议回答：模块内的接口、业务、数据库访问更集中，订单和支付边界更清楚；项目变大后，比全局 controller/service/mapper 分层更容易维护。

### 2.2 `class`、`interface` 和 `record`

项目里三者用途不同：

- `class`：包含行为和状态，例如 `OrderService`、`AuthController`。
- `interface`：描述能力或契约，例如 `OrderMapper`。MyBatis 在运行时为它生成代理对象。
- `record`：主要承载不可变数据，例如 [CreateOrderRequest.java](../backend/src/main/java/dev/meteor/order/dto/CreateOrderRequest.java) 和 [OrderResponse.java](../backend/src/main/java/dev/meteor/order/dto/OrderResponse.java)。

```java
public record OrderResponse(long id, OrderStatus status, long totalAmountCents) {
}
```

`record` 自动生成构造方法、字段访问方法、`equals`、`hashCode` 和 `toString`。读取 ID 写 `response.id()`，不是 `response.getId()`。

请求 DTO 使用 record 的紧凑构造器做轻量规范化：

```java
public CreateOrderRequest {
    idempotencyKey = idempotencyKey == null ? null : idempotencyKey.strip();
}
```

这里的 `条件 ? 值1 : 值2` 是三元表达式。它避免对 `null` 调用 `strip()` 导致空指针。

面试追问：为什么 DTO 用 record，数据库插入参数却有普通 class？

建议回答：DTO 创建后不应被修改，适合 record；插入参数需要让 MyBatis 把数据库生成的主键写回 `id`，所以 `OrderInsert` 使用可变 class。

### 2.3 字段、构造器和依赖注入

```java
private final ProductMapper productMapper;
private final OrderMapper orderMapper;

public OrderService(ProductMapper productMapper, OrderMapper orderMapper) {
    this.productMapper = productMapper;
    this.orderMapper = orderMapper;
}
```

- `private`：只有当前类能直接访问。
- `final`：构造后引用不能换成另一个对象。
- `this.orderMapper`：当前对象的字段。
- 构造器参数由 Spring 容器注入。

项目采用构造器注入，因为依赖明确、字段可保持 `final`，单元测试也能直接传入 stub 或 mock。这里没有必要使用字段上的 `@Autowired`。

### 2.4 方法参数、返回值和基本类型

```java
public OrderResponse createOrder(long userId, CreateOrderRequest request)
```

- `public`：其他类可以调用。
- `OrderResponse`：返回类型。
- `createOrder`：方法名。
- 括号内是参数。
- `long` 是基本类型，项目用它表示数据库 BIGINT 主键和以分为单位的金额。

金额使用 `long totalAmountCents`，不使用 `double`。原因是浮点数存在二进制精度问题，交易金额必须能够精确比较。当前项目只支持 CNY，数据库也有检查约束。

### 2.5 `==`、`!=` 和 `.equals()`

项目中可以看到：

```java
existing.productId() != request.productId()
!existingEvent.providerTransactionId().equals(request.providerTransactionId())
```

- `long` 是基本类型，可以用 `==` 或 `!=` 比较数值。
- `String` 是对象，业务内容比较使用 `.equals()`。
- `!` 表示逻辑取反。
- 用 `==` 比较两个字符串，比较的是引用是否相同，不是文字内容是否相同。

这是面试常问语法，但要结合项目回答：支付交易号是字符串，所以必须按内容比较。

### 2.6 `Optional` 和“查不到数据”

Mapper 的查询返回：

```java
Optional<OrderSnapshotProjection>
```

`Optional<T>` 表示“可能有一个 T，也可能没有”，比直接返回 `null` 更明确。项目有两种常见处理：

```java
.orElse(null)
```

表示暂时转成 `null`，随后进入自定义分支；以及：

```java
.orElseThrow(() -> new PaymentOrderNotFoundException(orderId))
```

表示查不到就通过 Lambda `() -> ...` 创建并抛出异常。

面试不要说 Optional 能消灭所有空指针。它只是把“可能不存在”写进返回类型，调用者仍必须正确处理。

### 2.7 异常和统一错误响应

[GlobalExceptionHandler.java](../backend/src/main/java/dev/meteor/web/error/GlobalExceptionHandler.java) 使用：

```java
@ExceptionHandler(PaymentConflictException.class)
@ResponseStatus(HttpStatus.CONFLICT)
```

Service 只表达业务失败，例如金额不匹配、幂等键冲突；全局异常处理器把异常转换成稳定的 HTTP 状态码和错误码。前端不用解析 Java 异常文字，而是处理 `409 PAYMENT_CONFLICT` 等 API 结果。

`try/catch` 在项目里还用于处理数据库唯一键竞争：

```java
try {
    orderMapper.insertOrder(order);
} catch (DuplicateKeyException exception) {
    // 另一个并发请求可能已经创建成功，重新读取并判断
}
```

这不是“忽略异常”。它把可以预期的并发碰撞转换为幂等结果；无法解释的异常仍继续抛出。

### 2.8 泛型和集合在本项目中的位置

`List<String>` 表示元素只能是字符串的列表。安全配置中的 `List.of(...)` 创建一组 Session 策略，用户主体中的角色也是集合。

你现在不需要单独背所有集合 API。面试前只要能说清：

- `List` 有顺序、可重复；适合一组订单项或处理策略。
- `Set` 不重复；适合角色集合，避免同一角色重复。
- `Map` 是键值映射；前端的 `Record<string, string>` 与这个思想相近。
- Java 内存集合只能约束单进程中的数据，不能代替数据库唯一约束。

### 2.9 `InputStream`、装饰流和 Spring `Resource`

下载服务没有把文件先读成 `byte[]`，而是让字节依次经过摘要流：

```java
try (DigestInputStream input = new DigestInputStream(source, digest)) {
    sizeBytes = input.transferTo(OutputStream.nullOutputStream());
}
```

- `InputStream` 表示可以顺序读取的字节来源。
- `DigestInputStream` 包住原始流；每读一段字节，就把同一段字节交给 `MessageDigest` 更新 SHA-256。这是装饰器模式在 JDK I/O 中的实际用法。
- `transferTo(...)` 持续分块复制并返回总字节数；目标是 `nullOutputStream()`，表示第一次读取只做计数和摘要，不保存文件内容。
- try-with-resources 保证正常结束和异常路径都会关闭流。

校验成功后，Service 返回 `Resource`：

```java
return new DownloadFilePayload(filename, mediaType, sha256, sizeBytes, resource);
```

Controller 的返回类型是 `ResponseEntity<Resource>`。Spring 的消息转换器在写 HTTP 响应时重新打开资源并分块复制，JVM 堆内存不会随文件大小等比例增长。当前项目把 Classpath 打包素材按部署约束视为不可变，所以“事务内先校验，提交后再打开并响应”可以接受；若运行时文件可能被外部改写，这个假设就不成立。将来接外部对象存储时还要绑定对象版本或 ETag，不能假定两次打开得到相同内容。

## 3. Spring Boot：注解背后发生了什么

### 3.1 启动类和组件扫描

[MeteorApplication.java](../backend/src/main/java/dev/meteor/MeteorApplication.java) 中：

```java
@SpringBootApplication
@MapperScan({ "dev.meteor.product.mapper", ... })
```

- `@SpringBootApplication` 开启自动配置、组件扫描和配置类能力。
- `@MapperScan` 告诉 MyBatis 去哪些包寻找 Mapper 接口并创建代理。
- `SpringApplication.run(...)` 启动 Spring 容器和内嵌 Tomcat。

注解本质上是元数据，不是看到注解就“自动拥有业务逻辑”。真正的行为由 Spring/MyBatis 在启动和请求期间读取这些元数据后提供。

### 3.2 Controller 只处理 HTTP 边界

[OrderController.java](../backend/src/main/java/dev/meteor/order/controller/OrderController.java)：

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {
    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public OrderResponse createOrder(...)
}
```

- `@RestController`：返回对象会被序列化成 JSON。
- `@RequestMapping`：类级别公共路径。
- `@PostMapping`：处理 POST。
- `@RequestBody`：把 JSON 转成 Java record。
- `@Valid`：执行 DTO 上的校验注解。
- `@AuthenticationPrincipal`：取得当前 Session 中的已登录用户。
- `201 Created`：表达资源已经创建，比一律返回 200 更准确。

Controller 没有核价、插表或支付判断，这些放在 Service。这样 HTTP 细节和业务规则不会混在一起。

### 3.3 Bean Validation 只负责输入形状

```java
@Positive long productId,
@NotBlank @Size(max = 100) String idempotencyKey
```

这些注解能拒绝负数 ID、空字符串和超长输入，但不能证明商品存在、套餐在售或用户有权限。后几项属于业务校验，必须去 Service 和数据库判断。

面试追问：前端已经校验了，后端为什么还要校验？

建议回答：前端可以被绕过，请求也可能来自脚本或旧版本客户端；服务端才是可信边界。

### 3.4 `@Transactional` 的真实含义

`OrderService.createOrder` 和 `PaymentService.applyTestPayment` 都有 `@Transactional`。

它表示 Spring 通过代理在方法进入时开启事务，正常返回时提交，未捕获的运行时异常通常触发回滚。支付链路中的以下操作必须作为一个整体：

1. 锁定并读取订单。
2. 写入支付尝试。
3. 写入支付事件。
4. 把支付尝试改为成功。
5. 把订单改为已支付。

如果第 4 或第 5 步失败，前面的写入不能单独留下，否则数据库会出现“有成功事件但订单仍待支付”的矛盾状态。

面试常见坑：同一个类内部直接调用自己的 `@Transactional` 方法，可能绕过 Spring 代理；本项目当前从 Controller 调用 Service Bean，不存在这个自调用问题。

### 3.5 Security 过滤器先于 Controller

请求并不是一进来就到 Controller。Spring Security 会先检查：

1. 当前路径是否允许匿名访问。
2. Session Cookie 能否恢复 Authentication。
3. POST 请求是否携带有效 CSRF token。
4. 通过后才进入 Controller。

所以缺少 CSRF 的登录请求会先得到 403，并不会进入密码校验。未登录访问受保护接口得到 401。

## 4. 登录链路：Session、CSRF、BCrypt 怎么一起工作

### 4.1 为什么项目选择 Session

当前前后端通过同站点 `/api` 代理工作，Session 方案简单且适合浏览器后台：

- 密码验证成功后，服务端把认证信息保存在 Session。
- 浏览器保存 `JSESSIONID` Cookie。
- 后续请求带 Cookie，服务端恢复身份。
- 退出时服务端能使 Session 失效。

面试时不要说 JWT 一定比 Session 高级。JWT 适合不同部署和无状态需求，但撤销、刷新、泄漏处理也更复杂。当前项目没有跨域多客户端需求，Session 是合理取舍。

### 4.2 BCrypt 为什么不能解密

数据库保存的是 BCrypt 哈希，不是可逆加密后的密码。登录时用用户输入与哈希进行匹配。BCrypt 自带盐并且计算成本可调，降低彩虹表和高速暴力破解风险。

不能说“BCrypt 绝对安全”；仍需配合强密码、登录限流、HTTPS、凭据保护和密码重置策略。当前项目只完成本地演示账号认证，还没有注册和找回密码。已知密码演示账号默认被认证层拒绝，只有本地显式设置 `METEOR_DEMO_ACCOUNTS_ENABLED=true` 才启用。

### 4.3 CSRF 防什么

浏览器会自动携带 Session Cookie。恶意网站可能诱导已登录用户向 Meteor 发送写请求，因此服务端还要求攻击者拿不到的 CSRF token。

[auth.ts](../frontend/src/api/auth.ts) 先调用 `/api/auth/csrf`，再用动态请求头：

```ts
[token.headerName]: token.token
```

方括号表示对象的属性名来自变量。`credentials: 'include'` 表示 fetch 要携带 Cookie。

登录和退出会轮换 token，因此前端遇到 403 会重新获取一次。生产环境还需要 HTTPS、合理的 Cookie `Secure`／`SameSite` 设置和反向代理配置。

## 5. 下单链路：最值得面试深挖的部分

### 5.1 为什么请求体没有金额

前端只提交：

```json
{
  "productId": 1001,
  "packageId": 2001,
  "idempotencyKey": "..."
}
```

金额由 `OrderService` 根据数据库里的在售套餐重新读取。如果相信前端金额，用户可以把 1900 分改成 1 分。

### 5.2 为什么保存订单快照

`order_items` 保存商品标题、套餐名、单价和币种快照。商品以后改名或涨价，历史订单仍应显示购买当时的事实。

这是一种有意的数据冗余。面试时不要只说“数据库要范式化”；交易事实通常需要快照，不能每次回查当前商品表重建历史。

### 5.3 幂等不等于“不重复点击”

幂等含义是：相同用户、相同幂等键、相同业务参数重复请求，得到同一个订单；相同幂等键却换了商品或套餐，返回 409。

项目采用两层保护：

1. Service 先按 `(userId, idempotencyKey)` 查询，快速返回已有结果。
2. 数据库唯一约束 `uq_order_user_idempotency` 处理两个请求同时到达的竞争。

阶段审查又补了第三步：如果插入发生 `DuplicateKeyException`，失败请求用 `FOR UPDATE` 当前读重新读取胜出的订单；参数相同就返回它，参数不同就报冲突。普通一致性读在 MySQL `REPEATABLE READ` 下可能仍停留在旧快照，不能用于这次恢复。

### 5.4 为什么不能只“先查再插”

两个线程可能同时查询到“不存在”，然后同时插入。这叫检查与执行之间的竞争窗口。只有数据库唯一约束能在最终写入点做原子裁决。

这是本项目非常好的面试点：应用层判断改善体验，数据库约束保证最终正确性。

## 6. 支付链路：事务、状态机、行锁和事件幂等

### 6.1 为什么支付事件单独建表

- `payment_attempts` 表示某个订单的一次支付尝试及其状态。
- `payment_events` 表示提供方发来的事件事实。

支付回调可能重复、延迟或乱序。如果只在 `orders` 上写一个 `paid=true`，就无法判断某个事件是否处理过，也缺少审计依据。

### 6.2 `SELECT ... FOR UPDATE` 做了什么

支付开始时通过 `findByIdAndUserIdForUpdate` 查询订单。`FOR UPDATE` 会在当前事务中锁定目标订单行，使针对同一订单的并发支付事件依次判断和更新状态。

它不是“锁整个数据库”，通常锁定命中的索引记录；锁会在事务提交或回滚时释放。事务应保持短小，不能在持锁期间调用缓慢的外部网络接口。

### 6.3 为什么有了行锁还要唯一约束

行锁解决“同一订单同时处理”的串行化；唯一约束解决“同一提供方事件 ID 或交易 ID 不能重复”。它们保护的维度不同，不能互相替代。

当前唯一约束包括：

- 一个订单最多一个支付尝试。
- `(provider, provider_transaction_id)` 唯一。
- `(provider, provider_event_id)` 唯一。

### 6.4 状态转移为什么写进 UPDATE 条件

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = ? AND user_id = ? AND status = 'PENDING_PAYMENT'
```

`status = 'PENDING_PAYMENT'` 不是多余判断。它让数据库只允许预期的 `PENDING_PAYMENT → PAID` 转移；更新行数不是 1 时，Service 抛出冲突并让事务回滚。

### 6.5 enum 为什么比状态字符串安全

`PaymentAttemptStatus` 把支付尝试限定为 `PENDING`、`SUCCEEDED`、`FAILED` 和 `RECONCILING`。Projection、插入参数和 Service 使用同一个类型：

```java
if (!attempt.status().acceptsSuccess()) {
    throw new PaymentConflictException(...);
}
```

如果写成字符串，`"SUCESS"` 这类拼写错误只有运行到对应分支才会暴露；enum 中不存在的常量会直接导致编译失败。MyBatis 默认按 enum 名称读写，所以数据库仍保存原有文本值；Jackson 也把 API 响应序列化为同名字符串。数据库 CHECK、Java enum 和 TypeScript 联合类型共同约束同一组词汇。

enum 只让状态集合和局部判断更明确，并不会自动形成完整状态机。当前代码只实现支付尝试的 `PENDING → SUCCEEDED`，失败重试和退款仍未实现。

### 6.6 本地测试支付的边界

`PaymentController` 使用：

```java
@ConditionalOnProperty(
    name = "meteor.test-payment.enabled",
    havingValue = "true"
)
```

默认配置下 Controller 不会注册，访问接口返回 404；只有本地显式设置 `METEOR_TEST_PAYMENT_ENABLED=true` 才启用。

这只是防止误暴露测试入口，不等于真实支付实现。真实支付还需要签名校验、原始事件 Inbox、异步重试、对账、退款和密钥管理。

对应的 `PaymentControllerDisabledWebTest` 在配置关闭时断言接口返回 404；`PaymentControllerWebTest` 在配置开启时分别检查匿名 401、缺少 CSRF 的 403、非法 DTO 的 400、成功 JSON、业务冲突 409 和资源隐藏 404。`@WebMvcTest` 只启动 MVC 相关上下文，适合验证路由、安全过滤器、序列化和异常映射，不负责证明真实数据库事务。

订单入口使用相同分层。`OrderControllerWebTest` 的请求 JSON 把幂等键写成 `" checkout-001 "`，随后用 Mockito 验证 Controller 传给 Service 的 `CreateOrderRequest` 已变成 `"checkout-001"`。这证明 Jackson 创建 record 时会执行 compact constructor；另外 8 项测试覆盖匿名 401、无 CSRF 403、Bean Validation 400、残缺 JSON 400、幂等冲突 409、套餐不可售 404、用户范围列表和外部订单隐藏。它们仍不执行服务端核价或 MySQL 事务。

### 6.7 为什么错误响应也需要统一类型

业务异常由 `GlobalExceptionHandler` 返回 `ApiErrorResponse`：

```java
public record ApiErrorResponse(
        String code,
        String message,
        String requestId,
        Instant timestamp
) {}
```

401 和 403 在请求到达 Controller 之前由 Spring Security 过滤器产生，因此不会经过 `@RestControllerAdvice`。`SecurityConfig` 注入 Jackson `ObjectMapper`，把相同 record 写入响应：

```java
objectMapper.writeValue(
    response.getWriter(),
    new ApiErrorResponse(
        code,
        message,
        RequestCorrelationFilter.requestId(request),
        Instant.now()
    )
);
```

使用序列化器可以稳定处理 JSON 转义和时间格式，也让前端只维护一种错误结构。残缺 JSON 会触发 `HttpMessageNotReadableException`，非数字路径变量会触发 `MethodArgumentTypeMismatchException`；全局处理器都将它们转换为 `INVALID_ARGUMENT`，并使用固定公开消息，避免把 Jackson 或类型转换内部信息返回给客户端。

### 6.8 请求编号、MDC 与日志关联

文件：[RequestCorrelationFilter.java](../backend/src/main/java/dev/meteor/web/request/RequestCorrelationFilter.java)。请求编号（request correlation ID）是一段用于把同一次 HTTP 请求的响应和日志关联起来的标识。本项目使用 `X-Request-Id`：

1. 客户端可以传入只含字母、数字、点、下划线和连字符的 1～64 位编号。
2. 缺失或格式不安全时，后端使用 `UUID.randomUUID()` 生成新编号。
3. 编号同时写入请求属性、响应头和 SLF4J MDC。
4. 统一错误 JSON 从请求属性读取同一编号。
5. 请求结束后在 `finally` 中清理或恢复 MDC，防止线程池复用时把上一个请求编号带到下一个请求。

核心结构：

```java
String requestId = resolveRequestId(request.getHeader(HEADER_NAME));
String previousRequestId = MDC.get(MDC_KEY);

request.setAttribute(REQUEST_ATTRIBUTE, requestId);
response.setHeader(HEADER_NAME, requestId);
MDC.put(MDC_KEY, requestId);

try {
    filterChain.doFilter(request, response);
} finally {
    if (previousRequestId == null) {
        MDC.remove(MDC_KEY);
    } else {
        MDC.put(MDC_KEY, previousRequestId);
    }
}
```

MDC 是“Mapped Diagnostic Context”，可以理解为当前线程日志附带的一组键值。`application.yml` 在日志级别区域输出 `%X{requestId}`，所以过滤器、Controller、Service 和 Mapper 在同一请求线程写出的日志都能带相同编号。

过滤器会记录方法、经过遮蔽的路径、状态码和耗时。`/api/downloads/{真实一次性 token}` 在日志中固定写成 `/api/downloads/{token}`，避免把短时凭证泄漏到日志。

前端 `http.ts` 优先读取错误 JSON 的 `requestId`，JSON 不可读时退回响应头；`ApiError` 将编号附在页面错误文字后，用户可以提供编号协助查日志。

`RequestCorrelationFilterTest` 验证三件事：安全的客户端编号会保留；包含空格等不安全输入会被 UUID 替换且请求结束后 MDC 被清理；一次性下载 token 会被遮蔽。`AuthControllerWebTest` 证明安全过滤器产生的 403 使用同一编号，`ProductControllerWebTest` 证明 Controller 业务异常映射出的 404 也使用同一编号。

当前能力只覆盖单个 Spring Boot 请求。它没有跨消息队列或跨服务传播 trace context，也没有集中日志、指标、告警和 OpenTelemetry；面试时应称为“请求日志关联”，不能称为完整可观测性平台。

## 7. MyBatis 和 SQL：Java 怎么访问数据库

### 7.1 Mapper 接口不是手写实现类

`OrderMapper` 是 interface，只声明 Java 方法；对应 SQL 位于 `backend/src/main/resources/mapper/OrderMapper.xml`。MyBatis 根据相同的 namespace 和方法 id 创建代理对象；Service 调用接口方法时，代理负责绑定参数、执行 SQL、映射结果。

```java
@Param("orderId") long orderId
```

`@Param` 给 SQL 占位表达式 `#{orderId}` 一个稳定名字。`#{...}` 使用预编译参数绑定，不应改成字符串拼接。

### 7.2 生成主键怎么回到 Java 对象

```xml
<insert id="insertOrder"
        useGeneratedKeys="true"
        keyProperty="id"
        keyColumn="id">
```

插入订单后，MyBatis 把数据库生成的自增 ID 写回 `OrderInsert.id`，随后用这个 ID 插入 `order_items`。

订单快照和订单详情查询使用 `<sql>` 定义公共字段与 JOIN，再通过 `<include refid="..."/>` 引用。这样新增快照字段时只改一个公共片段；普通查询和 `FOR UPDATE` 查询仍保留各自的 WHERE 与锁语义。

### 7.3 Flyway 为什么不能改旧迁移

V1～V12 是当前数据库演进历史。Flyway 保存已执行迁移的版本和校验和；修改已经执行的 SQL 会导致不同环境历史不一致。

下一次结构变化应新增 V13，而不是回头改 V4、V5 或其他已执行迁移。面试可将其解释为“数据库结构也需要可追踪、可重复的版本管理”。

### 7.4 约束与索引分别解决什么

- 主键：唯一标识一行。
- 外键：订单项不能指向不存在的订单。
- UNIQUE：幂等键、事件键和交易键不能重复。
- CHECK：金额非负、状态值和币种落在允许范围。
- INDEX：加速按用户、状态或时间的查询。

索引不是越多越好；写入时也要维护索引。应根据查询模式设计并用执行计划验证，当前项目还没有做大数据量压测。

## 8. Vue 与 TypeScript：前端代码怎么读

### 8.1 `type` 是编译期契约

[orders.ts](../frontend/src/api/orders.ts) 定义：

```ts
status: 'PENDING_PAYMENT' | 'PAID' | 'CLOSED' | 'REFUNDED'
```

这是字符串字面量联合类型，限制代码只能使用列出的状态。TypeScript 类型编译后不会在浏览器运行，因此不能替代后端校验。

### 8.2 `async`／`await` 和 Promise

`fetch` 返回 Promise。`await` 等待异步结果，但不会把网络请求变成同步阻塞整个浏览器。函数标记为 `async` 后总会返回 Promise。

```ts
const response = await fetch('/api/orders', options)
if (!response.ok) throw new ApiError(...)
return (await response.json()) as OrderResponse
```

`as OrderResponse` 是类型断言，不会验证服务端 JSON。更严格的项目会在运行时使用 schema 校验库；当前项目依赖前后端契约和测试。

### 8.3 模板字符串和动态路径

```ts
`/api/orders/${orderId}/test-payment`
```

反引号字符串允许 `${...}` 插值。这里把订单 ID 放进 URL 路径。

### 8.4 前端路由守卫不是服务端权限

[router.ts](../frontend/src/router.ts) 的 `beforeEach` 用于控制页面导航体验，但用户可以绕过浏览器路由直接请求 API。因此真正权限必须由 Spring Security 和业务查询中的 `userId` 保证。

当前路由只有在 Vite 开发模式且后端不可用时才允许本地角色回退；生产构建失败关闭，不信任 localStorage 角色。无论哪种模式，后端始终是最终权限边界。

### 8.5 统一 HTTP 客户端

`auth.ts`、`orders.ts`、`payments.ts` 原先重复处理 CSRF、错误解析和 403 重试，现已提取到 `frontend/src/api/http.ts`。写请求共用 token 缓存，403 时刷新并只重试一次；登录／退出后清除缓存，避免继续使用 Session 轮换前的 token。

这次重构的价值不是少写几行，而是让所有写请求遵守同一套安全边界。后续 API 只描述路径、请求体和响应类型，不再各自复制 token 状态机。

## 9. 面试官最可能追问的 20 个问题

### 1. 这个项目解决什么问题？

回答重点：数字作品从展示、登录、下单、本地测试支付到来源权益和内容库的交易基础；当前权益已完成，真实支付和文件交付仍在开发。

### 2. 你负责了什么？

只说自己能解释和验证的内容：Session 登录、CSRF、服务端核价、订单快照、幂等下单、支付事件去重、事务内发放来源权益、历史回填和用户资源隔离。不要把未来设计说成已实现。

### 3. 为什么价格不能由前端传？

客户端不可信。前端只传商品和套餐标识，服务端从在售套餐读取价格并保存快照。

### 4. 为什么订单还要保存商品标题和套餐名？

保留交易发生时的事实，避免商品改名、套餐下架或改价后历史订单变化。

### 5. 什么是幂等？

同一业务请求重复执行，最终效果与执行一次一致。本项目用“用户 + 幂等键”识别同一次下单意图。

### 6. 只在代码里先查一次够不够？

不够。并发请求可能同时查到不存在；数据库唯一约束负责最终裁决，应用捕获冲突后恢复成稳定结果。

### 7. 为什么订单幂等键要和 userId 组合？

不同用户可能生成相同客户端键，不应该互相冲突；幂等范围是单个用户的下单请求。

### 8. 为什么不用浮点数存金额？

浮点表示有精度误差。项目用最小货币单位“分”的整数和三字符币种。

### 9. `@Transactional` 保证了什么？

保证本地数据库多个写操作作为一个原子单元提交或回滚；它不自动保证外部支付平台与本地数据库的分布式原子性。

### 10. 为什么使用 `FOR UPDATE`？

同一订单并发处理支付事件时锁定订单行，让状态读取和更新串行发生，避免两个线程都基于旧状态继续。

### 11. 行锁会不会影响性能？

会增加同一热点订单的等待，但不同订单仍可并发。关键是命中索引、事务短小、不在持锁期间做远程调用。

### 12. 支付回调为什么会重复？

网络超时后提供方可能重试，消费者也可能重复投递。因此事件处理必须按提供方事件 ID 去重，不能假设只来一次。

### 13. 事件 ID 和交易 ID 为什么都唯一？

事件 ID 防同一回调重放；交易 ID 防同一笔支付被关联到两个订单。二者业务含义不同。

### 14. 为什么选择 Session 而不是 JWT？

当前是同站点浏览器应用，Session 易于服务端失效和权限变更；JWT 不是必然更安全或更先进，只有在无状态、多服务或多客户端需求明确时再权衡。

### 15. CSRF 和 XSS 有什么区别？

CSRF 利用浏览器自动携带 Cookie 伪造写请求；XSS 是恶意脚本进入可信页面执行。CSRF token 主要防前者，输出转义和内容安全策略等用于防后者。

### 16. 密码为什么用 BCrypt？

密码应做单向、带盐、成本可调的哈希。数据库泄漏时攻击者仍需逐个猜测，不能直接解密。

### 17. 前端路由拦截能算权限控制吗？

不能。它只改善 UI；服务端必须根据 Session 身份和资源归属再次授权。

### 18. MyBatis 和 JPA 为什么选 MyBatis？

当前项目希望明确展示 SQL、约束和锁语义，MyBatis 更直接。代价是映射和 SQL 需要手工维护。不要回答成某个框架绝对更好。

### 19. 现在最大的未完成风险是什么？

本地测试支付还不是可靠的真实回调系统；缺签名校验、Inbox 恢复、异步重试、对账和退款。权益、Release、冻结文件清单和 Classpath 文件的一次性下载已经创建，文件校验和 HTTP 响应也已改为固定内存的流式处理；但生产对象存储、对象版本校验、Range、失败审计和限流仍未实现。

### 20. 为什么先做 Release／Manifest，再做受控下载？

因为 Grant 只回答“谁因哪笔订单拥有哪个套餐”；Release 回答“有哪些不可变版本”，Manifest 回答“版本冻结时包含哪些文件”，下载授权最后回答“这次请求现在是否仍被允许”。当前四层已经完成本地最小闭环：五分钟票据只存哈希，消费时再次校验权益并记录响应准备审计。
