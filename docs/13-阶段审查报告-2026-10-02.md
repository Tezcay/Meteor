# Meteor 阶段审查报告（2026-10-02）

## 1. 结论

当前项目已经不是只有页面或设计稿的演示项目。登录、服务端核价下单、订单快照、幂等创建和本地测试支付事件都能在真实 MySQL 与浏览器中运行。核心链路适合写入简历，但简历必须明确写成“交易最小闭环”或“本地测试支付”，不能声称已经接入真实支付、退款、权益或文件交付。

本轮无需推翻现有架构。优先修复了会影响安全、并发正确性和面试可信度的问题，其余问题按维护性和后续里程碑排队。

## 2. 本轮发现并修复的问题

| 问题 | 风险 | 修复 |
| --- | --- | --- |
| V3 固定演示账号可能在部署环境继续可登录 | 已知密码账号暴露 | 演示账号默认拒绝登录，仅在 `METEOR_DEMO_ACCOUNTS_ENABLED=true` 时启用 |
| 订单并发插入失败后使用普通一致性读 | MySQL `REPEATABLE READ` 中可能读不到另一事务刚提交的订单并返回 500 | 冲突恢复改为 `SELECT ... FOR UPDATE` 当前读，并用真实并发 HTTP 请求验证 |
| 每次点击结账都生成新幂等键 | 响应丢失后重试可能创建第二笔订单 | 同一结账意图的幂等键保存在 `sessionStorage`，成功后才删除 |
| 登录身份按钮只换角色文案、不换邮箱 | 容易用错演示账号 | 身份、邮箱和说明同步切换 |
| 生产页面会展示已知演示密码 | 信息泄露与误导 | 演示身份按钮和已知密码只在 Vite 开发模式显示 |
| 路由守卫离线时信任 `localStorage` 角色 | 前端可能展示不属于用户的页面 | 仅开发模式允许本地回退，生产环境失败关闭；后端仍是最终权限边界 |
| 下单和测试支付只要求“已认证” | 管理员等非购买角色也可能调用 | 接口限制为 `USER`／`CREATOR` |
| 测试支付接口默认注册 | 部署误暴露非真实支付入口 | 默认关闭，仅在 `METEOR_TEST_PAYMENT_ENABLED=true` 时注册 |
| 字体在每个页面预加载但并未立即使用 | 浏览器重复产生性能警告 | 删除不必要的全局字体预加载 |

## 3. 验证证据

- 后端执行 `clean test`：26 项测试通过，0 失败、0 错误。
- 前端执行生产构建：通过。
- 前端生产依赖审计：0 个 high 及以上漏洞。
- 默认配置下演示账号登录返回 401，测试支付入口返回 404。

- Playwright 真实浏览器流程：买家登录 → 商品详情 → 结账 → 创建订单 → 模拟测试支付，最终订单为 `PAID`，控制台 0 错误。
- 浏览器和并发测试产生的订单、支付尝试与支付事件均已精确清理，三张表剩余测试记录为 0。

## 4. 当前仍存在的技术债

这些不是阻止当前阶段交付的问题，但后续应继续处理：

1. `auth.ts`、`orders.ts`、`payments.ts` 重复处理 CSRF 和错误响应，适合提取统一 API Client。
2. `BuyerPages.vue` 承载页面较多，新增权益和订单列表前应按业务页面拆分。
3. `GlobalExceptionHandler` 位于 `product` 模块，实际服务全局异常，后续应移动到公共 Web 包。
4. 当前真实 MySQL 并发验证是人工验收；有稳定 Docker 环境后应增加 Testcontainers 集成测试。
5. 仓库内尚未统一配置 CSP、`frame-ancestors`／点击劫持防护和 `nosniff`，部署时需要在应用或反向代理层补齐并验证。
6. 当前支付只是本地测试适配器，真实支付仍需要签名验真、Inbox、重试、超时和退款状态机。

## 5. 下一阶段优先级

最高优先级是实现 `EntitlementGrant`（购买权益）最小切片：支付事件成功后发放来源明确、可幂等恢复的权益；内容库只展示有效权益。它能把当前“付完钱仍看不到内容”的断点补上，也是简历和面试中最有价值的下一段业务闭环。

建议顺序：

1. 先写 Grant 的表结构、不变量、状态和接口验收条件。
2. 在支付事务或可靠事件消费中幂等发放 Grant。
3. 接通内容库查询，并补单元测试、真实 MySQL 验证和 Playwright 流程。
4. 再提取统一 API Client、拆分大页面、补自动化并发集成测试。
