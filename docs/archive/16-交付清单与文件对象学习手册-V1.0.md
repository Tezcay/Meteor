## 1. 这一步完成了什么

上一阶段只能回答：

> 当前用户购买的 Package 有哪些正式 Release？

这一阶段继续回答：

> 当前用户有权访问的某个 Release，冻结时到底包含哪些文件？

完整读取链路是：

```text
当前 Session 用户
  → ACTIVE EntitlementGrant
  → Grant 对应的 Package
  → 该 Package 下的 PUBLISHED Release
  → Release 唯一的 DeliveryManifest
  → 有序 ManifestItem
  → 不可变 FileObject 元数据
```

新增接口：

```http
GET /api/library/{grantId}/releases/{releaseId}/manifest
```

V12 已在这条读取链之后增加五分钟一次性下载票据、受控文件响应和响应准备审计。当前明确没有实现：文件上传、永久公开 URL、断点续传、生产对象存储和大文件流式传输；页面下载按钮只服务仓库内可校验的 Classpath 小文件。下载细节见[第六课](../24-第六课-一次性下载票据与受控文件响应-V1.0.md)。

## 2. 四个概念不能混在一起

### 2.1 Release

Release 是某个 Package 的一次正式发布，例如 Basic 套餐的 `v1.0.0`。它描述“这是哪个版本”，不直接承担文件存储。

### 2.2 DeliveryManifest

DeliveryManifest 是 Release 发布时冻结的完整交付快照。当前规则是一个 Release 最多一个 Manifest，由 `UNIQUE(release_id)` 保证。

### 2.3 ManifestItem

ManifestItem 是清单中的有序条目，保存：

- 在清单里的顺序；
- 面向用户的展示名称；
- 该文件的用途：`PRIMARY`、`GUIDE` 或 `BONUS`；
- 它引用哪个 FileObject。

### 2.4 FileObject

FileObject 表示内容固定的二进制对象，保存内部存储定位、原始文件名、媒体类型、字节数和 SHA-256。它不是下载链接，也不是前端页面上的一行文字。

同一个使用说明文件可以同时出现在 Basic 和 Pro 的 Manifest 中，因此 `FileObject → ManifestItem` 是一对多。这避免重复存储，也能准确证明两个版本引用的是同一份内容。

## 3. 为什么要拆成三张表

如果直接在 `releases` 表里加入 `file1`、`file2`、`file3`：

- 文件数量被固定；
- 无法为每个文件保存用途和顺序；
- 同一文件不能被多个版本复用；
- 新增第四个文件需要改表；
- 无法独立记录内容摘要和存储定位。

因此 V10 使用：

```text
delivery_manifests  版本的冻结交付快照
manifest_items      快照中的有序业务条目
file_objects        可复用的不可变文件对象
```

这是“版本快照”和“物理文件身份”分离，而不是为了单纯增加表数量。

## 4. V10 数据库约束

### 4.1 file_objects

关键字段：

```sql
storage_provider
storage_key
original_filename
media_type
size_bytes
content_sha256
```

重要约束：

```sql
UNIQUE (storage_provider, storage_key)
CHECK (size_bytes > 0)
CHECK (CHAR_LENGTH(content_sha256) = 64)
```

`storage_key` 是后端内部定位信息，API 不会把它返回给浏览器。否则将来切换存储提供方或改变目录结构时，会把内部实现变成外部契约。

### 4.2 delivery_manifests

```sql
UNIQUE (release_id)
```

它保证一个 Release 不会同时出现两份互相矛盾的正式清单。当前阶段没有提供修改 Manifest 的接口；正式内容发生变化时应创建新 Release。

### 4.3 manifest_items

```sql
UNIQUE (manifest_id, item_position)
UNIQUE (manifest_id, file_object_id)
CHECK (item_position > 0)
CHECK (role IN ('PRIMARY', 'GUIDE', 'BONUS'))
```

第一个唯一约束防止同一个位置出现两个文件；第二个防止同一个文件在同一清单中重复出现；角色检查防止数据库出现前端不认识的用途值。

## 5. 为什么种子文件是真实文件

V10 写入的 FileObject 并不是只存在于 SQL 中的假文件名。对应素材位于：

```text
backend/src/main/resources/delivery-fixtures/
```

迁移中的 `size_bytes` 和 `content_sha256` 来自这些文件的真实字节。`.gitattributes` 固定它们使用 LF 换行，避免不同系统检出代码后因换行转换导致摘要变化。

当前使用 `CLASSPATH` 作为本地学习环境的存储提供方。它不等同于 S3、OSS 或 MinIO；受控下载会读取这些真实字节，并在响应前再次核对 `size_bytes` 与 SHA-256。

## 6. 权限检查为什么必须是这个顺序

`DeliveryManifestService` 不是拿到 releaseId 后直接查询文件，而是：

```java
EntitlementGrantProjection grant = entitlementMapper
        .findActiveByIdAndUserId(grantId, userId)
        .orElseThrow(() -> new EntitlementGrantNotFoundException(grantId));

DeliveryManifestProjection manifest = manifestMapper
        .findPublishedByReleaseIdAndPackageId(releaseId, grant.packageId())
        .orElseThrow(() -> new DeliveryManifestNotFoundException(releaseId));
```

第一步证明“这个 Grant 属于当前用户且仍然有效”；第二步使用 Grant 中可信的 packageId，证明“这个 Release 属于用户购买的套餐且仍然正式发布”。

前端虽然同时提交 grantId 和 releaseId，但它们都只是待验证标识。用户可以手改 URL 或直接调用接口，所以不能因为页面只显示 Basic Release，就假设用户不会提交 Pro Release ID。

失败时统一使用 404，而不是告诉外部用户“这个 Release 存在，但属于另一个套餐”。这样减少资源枚举信息泄露。

## 7. Mapper SQL 在做什么

Manifest 头查询把 Manifest 和 Release 联接：

```sql
FROM delivery_manifests dm
INNER JOIN releases r ON r.id = dm.release_id
WHERE r.id = #{releaseId}
  AND r.package_id = #{packageId}
  AND r.status = 'PUBLISHED'
```

这不是单纯按主键查 Manifest。Package 归属和 Release 状态被放在同一条查询条件里，因此拿 Basic Grant 查询 Pro Release 会得到空结果。

文件条目查询按：

```sql
ORDER BY mi.item_position, mi.id
```

排序。`item_position` 是业务顺序，`id` 是稳定兜底顺序。虽然唯一约束已经保证同一 Manifest 的 position 不重复，保留 ID 排序仍让 SQL 意图完整清晰。

## 8. Java record 与响应 DTO

`DeliveryManifestProjection`、`ManifestItemProjection` 是 SQL 查询投影；`DeliveryManifestResponse`、`ManifestItemResponse` 是 API DTO。两者分离的意义是：数据库内部字段不应自动成为对外接口。

例如 FileObject 有 `storageProvider` 和 `storageKey`，但响应 DTO 没有。浏览器只得到：

- 展示名称；
- 原始文件名；
- 用途；
- MIME 类型；
- 字节数；
- SHA-256。

`stream().map(...).toList()` 把 Mapper 投影转换成不可修改的响应列表；`mapToLong(...).sum()` 汇总清单总字节数。汇总值由服务端从条目计算，前端只负责格式化显示。

## 9. 前端状态为什么按 releaseId 隔离

重构后，每个展开过的 Release 都有自己的 `DeliveryManifestPanel`，内部使用：

```ts
const requestKey = computed(() => `${props.grantId}:${props.releaseId}`)
const { data: manifest, status, error, reload } = useKeyedLoader(...)
```

键同时包含 grantId 与 releaseId，表达“用哪份权益读取哪个版本”。每个面板实例都有独立数据、状态、错误和 `AbortController`，所以一个版本加载失败不会取消或污染另一个版本。`ReleaseExplorer` 只负责当前展开哪个面板，不再负责清单请求本身。

面板第一次展开时才创建；收起后使用 `v-show` 保留实例和结果，再次展开不重复请求。组件真正卸载或键变化时，keyed loader 会取消旧请求并用序号拦截迟到响应。

页面把状态分成：

- 正在核对清单；
- 请求失败并可重试；
- 合法但清单为空；
- 清单有文件。

“空清单”和“请求失败”不是同一件事，不能共用一个空白 UI。

## 10. SHA-256 在这里解决什么

SHA-256 用于标识和校验内容：只要文件字节变化，摘要就会变化。它可以支持：

- 下载完成后的完整性校验；
- 判断两个版本是否复用了同一文件内容；
- 排查存储对象被意外替换；
- 后续实现内容寻址或去重。

SHA-256 不是下载权限，也不是数字签名。知道某个文件的摘要并不代表有资格下载它；如果攻击者能同时替换文件和数据库摘要，单独比较摘要也不能证明发布者身份。

## 12. 面试高频追问

### 问：Manifest 为什么不能直接保存一个 JSON 数组？

答：JSON 可以快速保存快照，但数据库很难用外键保证每个文件对象存在，也难以建立文件复用关系、按文件反查版本或对位置和角色做结构化约束。当前关系模型更适合需要授权、审计和复用的交付系统。

### 问：为什么 Manifest 属于 Release，不属于 Package？

答：Package 是长期售卖档位，Release 是一次不可变发布。同一个 Package 的不同 Release 可能包含不同文件，所以清单必须绑定具体 Release 才能还原历史交付事实。

### 问：为什么不把 storageKey 返回前端？

答：它是内部存储定位，可能暴露目录结构或被误当永久下载地址；对外应该通过受控下载接口重新校验权限，再返回短时凭证或直接流式传输。

### 问：数据库唯一约束和 Service 检查是否重复？

答：不重复。Service 提供清晰业务错误和正常流程；唯一约束保护并发、脚本或代码缺陷绕过 Service 后仍不能写入矛盾数据。

### 问：现在能否说完成了数字文件交付？

答：可以准确说完成了“本地 Classpath 小文件的一次性受控下载最小切片”：签发和消费都会重新校验当前权益，响应前校验文件完整性，并记录响应准备审计。不能把它描述成生产数字文件平台，因为对象存储、大文件流、断点续传、失败审计和限流尚未实现。

## 14. 已衔接的下一步：受控下载

V12 和 `download` 模块已经让系统安全回答“当前用户现在能否下载这个 ManifestItem”：

```text
Session 用户
  → ACTIVE Grant
  → PUBLISHED Release
  → ManifestItem 属于该 Manifest
  → FileObject 元数据与真实资源一致
  → 签发五分钟一次性票据，只保存 token 哈希
  → 消费时再次授权并返回经大小／SHA-256 校验的小文件
  → 记录 FILE_RESPONSE_PREPARED 审计
```

下载接口不接受浏览器提交的任意 storageKey，也不返回永久 Classpath／对象存储地址。票据过期、重复消费、Grant 撤销、Release 禁用、条目不属于清单或文件完整性失败都会被拒绝。实现与测试逐行讲解见[第六课](../24-第六课-一次性下载票据与受控文件响应-V1.0.md)。
