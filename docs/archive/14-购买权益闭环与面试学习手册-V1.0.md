学习目标：不是背一套通用语法，而是能沿着 Meteor 的真实代码解释“为什么付过钱的用户能看到自己的内容，而别人看不到”。

## 1. 这一阶段到底完成了什么

现在已经存在一条可运行、可验证的业务链路：

```text
买家登录
  → 选择商品套餐
  → 服务端按数据库价格创建 PENDING_PAYMENT 订单与订单快照
  → 本地测试支付事件到达
  → 锁定订单并校验用户、金额、币种、事件键和交易键
  → 同一个 MySQL 事务中记录支付事实、订单变为 PAID、创建 ACTIVE 权益
  → GET /api/library 只查询当前登录用户的 ACTIVE 权益
  → GET /api/orders 与 /api/orders/{id} 展示订单和权益状态
```

这里的“闭环”指本地可验证的交易到访问资格闭环，不等于真实商业支付和生产文件服务已经完成。本手册对应阶段当时尚无 Release 与文件清单；后续 V9～V12 已补齐只读版本、冻结文件元数据和 Classpath 小文件的一次性下载，但真实支付商签名、退款、生产对象存储、大文件流和完整失败审计仍未实现。

本阶段还完成了两个容易被忽略的工程动作：

- 旧的支付成功订单由 V7 迁移补发权益，避免升级后历史买家内容库为空。
- 前端不再用本地数组伪造已购内容，也不再提供“切换支付状态”的演示控件；页面只展示后端确认的订单和权益。

## 2. 先分清四个对象

| 对象 | 保存什么事实 | 不能代替什么 |
| --- | --- | --- |
| `Order` | 谁发起购买、订单总额、订单状态、幂等键 | 不能单独证明用户现在有访问资格 |
| `OrderItem` | 购买时的商品、店铺、套餐、价格和访问策略快照 | 不是实际文件，也不是支付流水 |
| `PaymentEvent` | 支付提供方报告过的事件事实 | 不能跳过本地金额校验后直接授权 |
| `EntitlementGrant` | 哪个用户因哪个订单项获得哪一套餐的访问资格 | 不是文件地址，也不是永久不可撤销的布尔值 |

最关键的关系是：

```text
Order 1 ── 1 OrderItem 1 ── 0..1 EntitlementGrant
```

当前订单只有一个订单项，所以是 1 对 1。以后如果允许购物车多商品，`Order` 到 `OrderItem` 会自然变成 1 对多，而每个订单项仍有自己独立的权益来源。

### 为什么不能给用户表加 `has_access = true`

假设同一用户买了 Basic 和 Pro 两个套餐，后来只退了 Pro：

- 设为 `false` 会错误撤销 Basic。
- 继续保留 `true` 又无法说明用户到底能访问哪个套餐。
- 无法追溯这份访问资格来自哪笔订单，也无法对单一来源执行退款撤权。

`EntitlementGrant` 把“主体、来源、资源范围、策略、状态”同时保存下来，所以退款、客服查询和审计都有明确依据。

## 3. 数据库为什么这样设计

### 3.1 V6：创建权益结构并补齐订单快照

V6 给 `order_items` 增加：

- `shop_name`：购买时的店铺名称快照。
- `access_policy`：购买时承诺的更新策略，当前只允许 `ALL_RELEASES`。

然后创建 `entitlement_grants`。核心字段的含义：

```sql
user_id       -- 权益属于谁
order_item_id -- 权益来自哪个购买项
product_id    -- 指向稳定商品身份
package_id    -- 访问哪个套餐范围
access_policy -- 能否包含未来发布版本
status        -- ACTIVE 或 REVOKED
granted_at    -- 何时生效
revoked_at    -- 何时撤销
```

核心约束不是装饰，它们承担最后一道正确性保护：

```sql
UNIQUE (order_item_id)
```

表示同一个订单项最多产生一条来源权益。即使应用重复执行发放 SQL，也不能产生第二条。

```sql
CHECK (
  (status = 'ACTIVE' AND revoked_at IS NULL)
  OR (status = 'REVOKED' AND revoked_at IS NOT NULL)
)
```

表示“有效但已有撤销时间”和“已撤销但没有撤销时间”都属于非法数据。业务代码可能有 Bug，数据库仍拒绝自相矛盾的状态。

```sql
INDEX (user_id, status, granted_at, id)
```

匹配内容库最常见的查询形状：先找某用户，再筛选有效权益，最后按发放时间倒序。索引不代表查询一定零回表；是否命中以及扫描行数仍要用 `EXPLAIN` 验证。

### 3.2 V7：为什么还要补历史数据

V6 生效前已经可能存在 `PAID` 订单。如果只创建空的权益表，新支付可以发放权益，但旧买家进入内容库会看不到任何内容。

V7 使用 `INSERT ... SELECT` 从已支付订单和订单项生成权益：

```sql
INSERT INTO entitlement_grants (...)
SELECT ...
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'PAID'
ON DUPLICATE KEY UPDATE id = entitlement_grants.id;
```

这个迁移可重复面对“部分数据已存在”的情况：唯一约束识别既有订单项，重复时执行无副作用更新，不会制造第二条权益。

要注意：已经在某个数据库执行过的 V6 不能再偷偷修改。否则 Flyway 校验和会变化，其他环境会拒绝启动。发现漏掉历史回填后新增 V7，正是正确的迁移方式。

## 4. 支付成功时如何保证不出现半成品

入口是：

```java
@Transactional
public PaymentResponse applyTestPayment(...)
```

`@Transactional` 让本地数据库写操作使用同一个事务。首次支付成功会执行：

1. `SELECT ... FOR UPDATE` 锁定属于当前用户的订单。
2. 校验事件键、交易键、金额、币种和订单状态。
3. 写 `payment_attempts`。
4. 写 `payment_events`。
5. 把支付尝试改为 `SUCCEEDED`。
6. 条件更新订单 `PENDING_PAYMENT → PAID`。
7. 创建或确认权益存在。
8. 提交事务。

如果第 7 步没有得到权益，代码抛出 `IllegalStateException`。因为异常离开事务方法，前面的支付记录和订单状态也会回滚；不会留下“订单显示已支付，但内容库没有权益”的半成品。

这个保证只覆盖同一个 MySQL 数据库事务，不覆盖真正支付平台的远程系统。真实支付需要 Inbox、重试、对账等恢复机制，不能把 `@Transactional` 说成分布式事务。

## 5. 权益发放 SQL 的三个关键点

`EntitlementMapper.ensureGrantForPaidOrder` 使用条件插入：

```sql
INSERT INTO entitlement_grants (...)
SELECT ...
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.id = #{orderId}
  AND o.user_id = #{userId}
  AND o.status = 'PAID'
ON DUPLICATE KEY UPDATE id = entitlement_grants.id
```

第一，`o.user_id = #{userId}` 把资源归属检查放进 SQL。调用者不能只知道订单 ID 就给任意订单发权益。

第二，`o.status = 'PAID'` 表示只有数据库已经确认支付的订单才是授权来源。前端显示成功、请求里传一个状态字符串，都不能绕过这个条件。

第三，`ON DUPLICATE KEY` 配合 `UNIQUE(order_item_id)` 使操作幂等。这里的 `id = entitlement_grants.id` 是“保持原值”的无副作用更新，不会创建第二条，也不会把已经撤销的权益偷偷重新激活。

### 为什么重复支付事件仍会调用一次权益确认

重复事件正常返回已有支付结果，但仍调用 `ensureEntitlement`。这是有意的“幂等恢复”：如果历史版本已经记录支付，权益却因旧代码或迁移问题缺失，合法事件重放可以补齐它。

恢复仍受三个边界约束：事件必须是已记录的合法事件、订单属于当前用户、订单状态必须是 `PAID`。它不是任意补发接口。

## 6. 内容库和订单接口如何隔离用户

新增接口：

| 方法与路径 | 作用 | 身份要求 |
| --- | --- | --- |
| `GET /api/library` | 当前用户的有效权益 | `USER` 或 `CREATOR` |
| `GET /api/orders` | 当前用户的订单列表 | `USER` 或 `CREATOR` |
| `GET /api/orders/{orderId}` | 当前用户的一笔订单和权益状态 | `USER` 或 `CREATOR` |

Controller 不接收前端传来的 `userId`，而是从 Spring Security 当前认证读取。Mapper 查询继续带上：

```sql
WHERE o.id = #{orderId}
  AND o.user_id = #{userId}
```

访问别人的订单返回 404，而不是告诉请求者“订单存在但你无权访问”。这样可以减少订单 ID 枚举带来的信息泄露。

内容库查询只返回：

```sql
WHERE eg.user_id = #{userId}
  AND eg.status = 'ACTIVE'
```

前端不能通过改 URL、localStorage 角色或请求参数查看他人的权益。前端路由守卫只是体验层，真正授权在服务端和 SQL 资源归属条件中完成。

## 7. 前端从 Demo 变成产品流程的变化

### 7.1 统一 HTTP 层

`frontend/src/api/http.ts` 集中处理：

- JSON／空响应解析。
- 后端错误消息转换。
- CSRF token 缓存。
- 写请求遇到 403 时刷新 token，并且只重试一次。

“只重试一次”很重要。无限重试会把权限错误变成请求风暴，也会掩盖真正的 Session 或配置问题。

登录成功后会清除旧 token 缓存，因为 Spring Security 登录时会轮换 Session 与 CSRF token。浏览器验收也观察到了这个边界：登录前的 token 不能继续用于登录后的创建订单请求。

### 7.2 页面不再编造业务状态

旧页面允许用户点击按钮把界面切成“等待支付／确认中／可使用”，内容库还能显示预览订单。这类组件适合早期视觉原型，却会让成品像 Demo，也可能让用户误以为状态来自后端。

现在：

- `/checkout/result?orderId=...` 调用订单详情接口。
- 只有真实 `PENDING_PAYMENT` 订单才显示本地测试支付按钮，而且仅开发构建可见。
- 只有真实 `PAID + ACTIVE grant` 才显示“访问权益已经生效”。
- `/library` 请求真实权益。
- `/orders` 和 `/orders/{id}` 请求真实订单。
- 加载、失败、空状态和成功状态分别处理。

这就是成熟产品与静态 Demo 的重要差别：页面状态由业务事实驱动，每个按钮都对应明确的用户任务和后端结果。

## 8. 用本项目学习 Java 语法

### 8.1 `record`：表达不可变的数据载体

```java
public record EntitlementGrantProjection(
        long id,
        long userId,
        String status
) {}
```

它等价于“主要用于携带数据的不可变类”。Java 自动生成构造器、`id()`／`userId()`／`status()`、`equals`、`hashCode` 和 `toString`。在本项目中 DTO 和 SQL 投影适合用 `record`，因为它们不应该在传递过程中随意变化。

### 8.2 `Optional<T>`：明确表示可能没有结果

```java
Optional<EntitlementGrantProjection> findByOrderIdAndUserId(...)
```

返回类型直接告诉阅读者“可能找不到”。服务层用：

```java
.orElseThrow(() -> new IllegalStateException(...))
```

`()` 表示 Lambda 没有参数，`->` 右边表示真正需要异常时如何创建。它不是立刻抛异常；只有 Optional 为空才执行。

### 8.3 `stream().map(...).toList()`：逐项转换

```java
return projections.stream()
        .map(LibraryService::toResponse)
        .toList();
```

可以读成：把数据库投影列表变成流；每一项交给 `toResponse`；收集成新列表。`LibraryService::toResponse` 是方法引用，等价于 `item -> toResponse(item)`。

### 8.4 构造器注入

```java
public LibraryService(EntitlementMapper entitlementMapper) {
    this.entitlementMapper = entitlementMapper;
}
```

左边的 `this.entitlementMapper` 是当前对象字段，右边是构造器参数。依赖从外部传入，生产环境由 Spring 注入，单元测试可以传入 Stub；因此业务代码不用自己连接数据库，也更容易测试。

### 8.5 `private static` 转换函数

`toResponse` 不访问某个 `LibraryService` 实例的状态，所以可以是 `static`；只在类内部使用，所以是 `private`。这比把映射逻辑散落在 Controller 中更容易读和测试。

## 9. 用本项目学习 SQL 语法

### `JOIN` 与 `LEFT JOIN`

- 内容库使用 `JOIN`：没有订单项或订单就不是完整权益，不应返回。
- 订单详情使用 `LEFT JOIN entitlement_grants`：待支付订单还没有权益，但订单本身仍应返回。

如果把订单详情的 `LEFT JOIN` 错写为 `JOIN`，所有待支付订单会从列表消失。这是面试常见追问。

### `#{userId}`

这是 MyBatis 参数占位，不是 JavaScript 模板字符串。MyBatis 使用预编译参数绑定，避免把值直接拼进 SQL。动态表名等结构不能靠普通参数占位，需要格外谨慎；本项目没有让客户端传表名。

### `ORDER BY granted_at DESC, id DESC`

先按发放时间从新到旧；时间完全相同再按主键倒序，保证排序稳定。

### 唯一约束与“先查再写”

只写“先查询不存在，再插入”仍有并发窗口：两个请求可以同时查到不存在。唯一约束是最终裁判，幂等 SQL让冲突变成稳定结果。应用检查用于友好行为，数据库约束用于最终正确性。

## 10. 用本项目学习 TypeScript 和 Vue

### 10.1 联合字面量类型

```ts
status: 'ACTIVE' | 'REVOKED'
```

表示这个字段只能是两个字符串之一。写成普通 `string` 会让拼写错误更晚才暴露。

### 10.2 泛型

```ts
apiGet<LibraryItemResponse[]>('/api/library')
```

尖括号告诉 TypeScript：这个请求成功后的 JSON 应被当作权益数组。它只提供编译期检查，不会自动验证服务器真的返回了这个结构；严格生产系统可再引入运行时 Schema 校验。

### 10.3 `ref` 与 `computed`

```ts
const order = ref<OrderDetailResponse | null>(null)
const orderId = computed(() => ...)
```

`ref` 保存会变化且要触发界面更新的状态；`computed` 从其他响应式值推导结果。模板里 Vue 会自动解包，所以写 `order.id`，脚本里则用 `order.value`。

### 10.4 `AbortController`

页面快速切换时，旧请求可能晚于新请求返回并覆盖页面。`AbortController` 在发起新请求或组件卸载时取消旧请求，减少过期响应污染 UI。

### 10.5 `v-if / v-else-if / v-else`

账户页按“加载 → 错误 → 数据或空态”的互斥顺序渲染。顺序有业务含义：请求未结束时不应提前显示“空内容库”，失败也不能伪装成“没有购买”。

## 11. 测试分别证明什么

单元测试当前覆盖：

- 正常支付会发放一条 ACTIVE 权益。
- 同一事件重放不重复写支付事实，但会确认权益存在。
- 已支付订单如果最终找不到权益，服务抛异常以触发事务回滚。
- 内容库只映射 Mapper 返回的有效权益，并能返回空列表。
- 订单列表和详情包含权益状态。
- 找不到或不属于当前用户的订单统一抛 `OrderNotFoundException`。

真实 MySQL 验收额外证明：

- V6、V7 能在 MySQL 8.0 执行。
- 首次支付与相同事件重放返回同一个 Grant ID。
- 数据库中同一订单项只有一条权益。
- 买家能查询自己的内容库和详情。
- 另一个已登录账号查询该订单得到 404，内容库没有该权益。

Playwright 浏览器验收证明：

- 登录、商品详情、结账、创建订单、测试支付、内容库、订单详情能串起来。
- 页面没有使用假订单填充成功状态。
- 桌面和 390px 手机宽度没有横向溢出；手机订单操作已改为单栏。
- 浏览器控制台没有 error。

V8 还会把固定演示账号默认改为 `LOCKED` 并替换已知密码哈希。应用每次启动都根据 `METEOR_DEMO_ACCOUNTS_ENABLED` 主动同步账号状态：默认继续锁死，只有本地明确开启时才装入演示凭据。这比仅在认证服务里“拒绝已知邮箱”多一层数据库状态保护。

单元测试快、定位准，但不能证明迁移 SQL能在真实 MySQL 执行；人工数据库／浏览器验收能覆盖集成，却不适合代替每次提交都跑的自动测试。两者互补。

## 12. 面试官高频追问与回答骨架

### 问：支付成功和发放权益为什么放同一个事务？

答：当前二者都在同一个 MySQL，放在同一事务可以避免订单已支付但权益缺失。发放后还会重新查询 Grant，不存在则抛异常回滚。真实支付平台在数据库之外，所以还要靠幂等事件、Inbox／重试和对账恢复，不能靠本地事务覆盖远程系统。

### 问：权益发放怎样保证幂等？

答：业务范围由 `PAID + userId + orderId` 限制，数据库以 `order_item_id` 唯一约束保证一个来源最多一条权益，插入使用无副作用的 `ON DUPLICATE KEY UPDATE`。支付事件重放会返回同一权益，不会重复创建或重新激活撤销记录。

### 问：为什么订单详情要用 LEFT JOIN？

答：权益是支付后才出现的可选关系。待支付订单没有 Grant 也应该在订单列表中出现；普通 JOIN 会把它过滤掉。

### 问：为什么访问别人订单返回 404，不返回 403？

答：查询从一开始就限定 `orderId + 当前 userId`。没有结果统一视为不存在，可以减少订单编号枚举造成的信息泄露。角色级权限仍由 Spring Security 控制。

### 问：历史 PAID 订单怎么办？

答：V7 做一次幂等回填，用支付事件处理时间或订单时间作为生效时间；V6 已执行后不能改原脚本，所以新增迁移。合法支付事件重放也保留了自愈路径。

### 问：现在为什么还不能说完成数字商品交付？

答：权益阶段完成时只有访问资格，不是文件；后续 V9～V12 已补齐不可变 Release、Manifest 和一次性下载。当前签发与消费都会重新检查撤权状态，并记录响应准备审计；仍缺生产对象存储、大文件流、Range、失败审计和限流，因此只能称为本地小文件下载最小切片。

### 问：目前有哪些已知边界？

答：订单仍是单商品；同一用户再次购买相同套餐尚未做业务拦截；没有退款状态机；本地测试支付不是实际支付商；2 项 Testcontainers 已有代码但因 Docker 不可用仍被跳过；当前下载只支持 Classpath 小文件、五分钟一次性票据、二次授权、完整性校验和响应准备审计，不是生产对象存储或大文件交付平台。

## 13. 简历写法

可以写：

> 基于 Spring Boot、MyBatis、MySQL 与 Vue 3 实现数字商品“下单—测试支付—权益发放—内容库”闭环；使用服务端核价和订单快照保存交易事实，并以 Session、资源归属查询和数据库约束隔离用户数据。

> 设计来源可追溯的 EntitlementGrant，在支付事务中以订单行锁、事件／交易唯一键和订单项唯一约束实现幂等发放；通过 Flyway 增量迁移回填历史已支付订单，并验证事件重放不重复授权。

不要写：

- “接入微信／支付宝／Stripe”，当前没有。
- “完成安全下载”，当前已有 Grant、Release 和 Manifest，但没有下载授权与受控文件流。
- “支持退款自动撤权”，当前只为未来状态保留结构。
- “经过高并发压测”，当前验证的是关键并发与幂等场景，不是压测。

## 15. V12 下载完成后的下一大块

Package 级 Release、冻结交付清单和 Classpath 小文件的一次性下载已经完成，详见 [Release 手册](15-发布版本Release学习手册-V1.0.md)、[Manifest 手册](16-交付清单与文件对象学习手册-V1.0.md) 和[第六课](../24-第六课-一次性下载票据与受控文件响应-V1.0.md)。下一阶段进入生产化边界：

1. 接入私有对象存储，让 `storage_key` 指向受保护的生产文件。
2. 使用流式响应或短时签名 URL，避免 `readAllBytes()` 占用完整文件内存。
3. 增加 Range／断点续传、限流、中断处理和失败下载审计。
4. 在退款成功后按来源撤销 Grant，并让未消费票据立即失效。

当前已经可以讲“从交易正确性走到资源授权与本地安全交付”；完成上述能力后，才能进一步描述成生产文件交付系统。
