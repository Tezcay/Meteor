# 多商家数字商品平台：项目需求与总体设计 V0.1

日期：2026-09-15  
状态：选题阶段草案，尚未确认开工，不代表导师已批准。  
用途：保存讨论成果、核对产品范围、指导后续原型和技术验证。

## 1. 项目背景与目标

当前用于规划专业实习课程项目，并保留后续发展为本科毕业设计的可能。两者可以分离；同学课程题目获批不能直接作为本项目毕设通过的依据。

开发者希望做出界面精致、普通用户能理解和使用的完整 Web 产品，同时具有可解释、可验证的后端工程内容。无需追求市场空白或原创算法，不以中间件数量衡量深度。

产品定位：多商家发布和维护数字模板、素材，买家发现、购买并持续获取其有权访问的文件，平台负责审核和交易管理。

核心问题：购买成功后，正确的用户能持续获得正确版本的内容；重复事件、处理失败、商品更新和权益撤销不会破坏这一关系。

## 2. 第一版用户与业务边界

### 2.1 角色

| 角色 | 主要能力 | 边界 |
| --- | --- | --- |
| 访客 | 浏览店铺、商品、预览和公开说明 | 无正式文件访问权 |
| 买家 | 下单、查看订单、访问内容库、下载、申请退款 | 只能访问自己的订单和权益 |
| 商家 | 申请入驻、维护店铺、管理商品和版本、查看本店订单 | 不得访问其他商家数据 |
| 平台管理员 | 审核入驻和发布申请、处理下架与退款等异常 | 操作留痕 |

草案建议：一个账号可以同时是买家和商家；每个商家账号管理一个店铺。暂不实现商家员工体系。以上为待确认的简化规则。

### 2.2 商品范围

- 优先支持文档、演示文稿、表格模板，以及图标、插画、界面素材包。
- 商品可以有基础包、完整包等套餐；套餐对应明确的交付文件集合。
- 支持图片预览、说明、文件格式、兼容信息、更新说明和商家提供的使用范围。
- 压缩包及视频可作为待下载文件；首版不提供通用在线文档转换、代码运行或压缩包自动解压。
- 视频预览仅作为可选能力，限定格式与大小，不建设完整课程播放系统。

### 2.3 明确不纳入首版

- 真实资金托管、商家提现、资金分账与税务结算。
- 跨店合并付款、多币种、复杂促销叠加、秒杀、积分体系。
- 多清晰度视频转码、直播、软件激活与 DRM。
- 完整客服聊天、推荐算法、公开社区、原生移动应用。
- 自动生成或保证商品的商业授权合法性。

商家入驻不等于必须实现真实资金分账。首版商家订单金额统计仅表示测试交易统计，不称为可提现余额。

## 4. 核心业务规则：草案默认值

以下是为使方案可落地而提出的默认规则，尚需用户确认，不视为已有产品事实。

### 4.1 交易

- 首版采用立即购买：一笔订单包含一个商品的一个套餐，不设跨店购物车。
- 支付使用可替换的测试实现；未接真实支付时，界面与报告明确标注。
- 金额使用精确表示，不使用浮点数直接计算金额。
- 订单保存商品名、商家、套餐、价格、使用范围说明及更新权益规则等快照；当前商品修改不回写历史订单。
- 客户端返回支付成功不直接作为支付依据；由服务端测试支付适配器产生并验证事件。
- 同一支付事件重复到达只产生一次有效业务结果。
- 晚到的支付、订单关闭后收到支付结果等情形进入明确的异常处理，不静默忽略。

### 4.2 套餐、版本与权益

- 套餐表示售卖内容的组合；版本表示某次实际发布的文件内容，两者分别建模。
- 首版建议规则：购买某套餐后可获取该套餐的现有版本与后续更新。大版本收费升级留待拓展。
- 已发布版本不直接覆盖文件；修订内容形成新版本并保留旧记录。
- 文件上传完成并核对元数据后，版本才可提交审核或发布。
- 不同套餐使用稳定标识。调整套餐名称或价格不改变老订单权益。
- 商品普通下架仅停止新购买；老用户仍可根据权益下载。
- 安全或侵权处置可能需要禁用具体文件，需与普通下架分开，记录原因，并向受影响用户展示不可用状态。

### 4.3 退款与访问

- 首版仅支持整单测试退款，不做部分退款和复杂金额分摊。
- 退款申请待处理期间权益保持原状；收到退款成功结果后撤销对应订单产生的后续访问资格。
- 被拒绝的退款保留原因；处理过程留痕。
- 如果未来允许多笔订单产生同一内容的权益，不能因一笔退款误撤其他有效权益。
- 已下载到用户设备的文件无法凭服务端撤权收回，不宣称彻底防复制。
- 签发的短时下载链接存在有效期窗口；若需要立即撤销，应采用不同的访问交付方案并单独评估成本。

### 4.4 入驻与审核

- 入驻流程：待审核 → 通过／驳回，可修改后重提。
- 商品与新版本：草稿 → 待审核 → 通过发布／驳回。
- 已发布商品的关键内容修改通过新修订提交审核，旧发布内容在审核期间保持稳定。
- 店铺停用停止发布与新销售；已有订单、下载和退款的处理需要单独规则，不直接级联删除。
- 首版不收集无必要的真实证件或银行资料；课程演示使用测试入驻信息。

## 5. 端到端流程

### 5.1 发布与购买

商家申请入驻 → 管理员审核 → 商家创建商品和套餐 → 上传正式文件并制作预览 → 提交发布审核 → 买家浏览并选择套餐 → 创建订单快照 → 测试支付确认 → 发放权益 → 内容库展示 → 校验权益并下载。

### 5.2 版本更新

商家上传新文件 → 创建新版本与更新说明 → 检查文件状态和套餐关联 → 审核发布 → 有权用户内容库显示更新 → 用户选择新版或允许访问的历史版本。

### 5.3 退款

买家申请 → 按角色权限处理 → 发起测试退款 → 接收退款结果 → 更新订单及权益 → 记录结果并通知。结果事件重复、晚到或处理失败时仍能恢复一致状态。

## 6. 用户端与管理端页面

### 用户端

1. 发现页：精选内容与分类入口，有限推荐位，不堆促销弹窗。
2. 分类／搜索页：商品卡片及有限筛选条件。
3. 店铺页：商家介绍、商品列表和必要联系信息。
4. 商品详情：大图预览、包含文件、适用格式、套餐差异、使用范围、更新说明。
5. 结账及结果页：确认套餐、价格与规则；处理中、成功、失败状态明确。
6. 内容库：已购商品、可用版本、更新提示、下载入口。
7. 订单详情：购买快照、处理记录与退款入口。

### 商家工作台

入驻申请、商品列表、商品编辑、文件与版本、审核结果、本店订单。先重视表单清晰和错误提示，不做复杂经营大屏。

### 平台管理端

入驻审核、商品审核、异常下架、订单与退款查询、失败任务查看和受控重试、审计记录。

### 视觉原则

- 使用柔和配色、清晰字体层级、圆角与留白，整体风格统一。
- 统一商品预览尺寸、背景和截图边距；封面与真实商品内容一致。
- 详情页先展示商品价值与内容，再展示购买规则；避免冗长重复海报。
- 购买后以内容库为主要入口，而不是迫使用户从订单列表找文件。
- 审核中、支付处理中、权益待恢复等状态不能被一个泛化的“失败”覆盖。
- 不照搬参考产品商标、文案和素材；参考信息结构与交互方式。

## 7. 总体技术设计建议

状态：建议方案，技术栈尚未最终确认。

- 前端：Vue 3 + TypeScript + Vite；样式与组件库待原型阶段选择。
- 后端：Spring Boot 模块化单体，先利用已有 Java 经验。
- 数据：PostgreSQL 或已有熟悉的关系数据库，落地时二选一；配套数据库迁移。
- 文件：对象存储接口，开发阶段可使用兼容实现；公开预览与私有交付内容分离。
- 部署：单应用服务、数据库、文件存储；采用容器化方式便于重现。
- 业务模块：账号权限、商家店铺、商品发布、订单支付、权益交付、售后、通知审计。
- 长任务：先以持久化任务记录实现重试和恢复；必要时再引入消息队列。缓存按实际需求引入。

订单与权益可在同一数据库事务内更新时，优先利用本地事务。通知等外部副作用独立处理；引入异步处理时保留业务唯一键、处理状态与补偿入口，不将“用了消息队列”等同于一致性已解决。

文件上传与数据库发布不能视为一个普通本地事务：区分上传中、可用、已发布和待清理文件；通过状态与清理任务处理未完成上传及孤立文件。应用不自动执行上传内容。

## 8. 概念数据关系

这不是最终表结构，暂不固定字段与索引。

| 对象 | 作用及关系 |
| --- | --- |
| 用户、角色 | 身份与访问范围 |
| 入驻申请、店铺 | 商家资格、审核历史与经营主体 |
| 商品、商品修订 | 公共售卖对象及待发布修改 |
| 套餐 | 同一商品的可购买选项 |
| 发布版本、文件对象、交付清单 | 某套餐在某版本实际包含哪些文件 |
| 订单、订单项快照 | 记录购买时的承诺与金额 |
| 支付尝试、支付事件 | 处理重复通知、异常结果与核对 |
| 权益 | 来源订单、可访问套餐、状态和更新规则 |
| 下载记录 | 记录访问结果，不把点击等同于文件下载完成 |
| 退款申请、退款事件 | 售后流程及结果 |
| 后台任务、站内通知、审计日志 | 恢复、反馈和操作追溯 |

主要关系：店铺拥有商品，商品有套餐，套餐关联版本交付清单；订单项指向购买对象并保留快照，订单产生权益，下载结合权益与发布状态校验。

## 9. 展示数据与测试数据

- 先准备约 12—20 个可用演示商品，分属少量测试店铺；数量是建议而非硬性要求。
- 至少 3 个商品含多套餐或多版本，用于演示差异化交付和更新。
- 演示文件采用自制或明确允许再分发的资源，保留来源、作者和许可信息。
- 预览从实际文件生成或制作，不用无关图片冒充商品效果。
- 测试价格、用户和订单明确是演示数据，不伪造真实经营成果。
- 大量性能测试数据单独生成，不与真实产品效果混为一谈。
- Unsplash 配图不直接打包为付费图库；具体资源依据其许可使用。

## 10. 验收与技术验证

| 场景 | 预期结果 |
| --- | --- |
| 未购买用户直接请求正式文件 | 拒绝访问，无永久公开文件地址泄漏 |
| 商家 A 请求商家 B 的订单或编辑接口 | 服务端拒绝，不能只靠页面隐藏 |
| 同一支付结果重复提交 | 一份有效订单结果，不重复发放权益 |
| 支付确认或权益处理期间故障 | 可重试恢复，不永久出现付款成功却无权益 |
| 用户支付后商品改价或改套餐 | 原订单快照与既有规则不被覆盖 |
| 文件尚未上传完成就尝试发布 | 阻止发布，展示可理解原因 |
| 发布新版 | 新旧文件可区分，符合规则的用户可访问更新 |
| 商品普通下架 | 禁止新购，旧权益按规则继续有效 |
| 退款成功 | 对应后续访问失效，历史记录仍可查询 |
| 支付结果晚到、退款事件重复 | 明确处理或进入异常队列，不错误反转状态 |

性能测试注明环境、数据量和负载方式，记录延迟和错误率，不把压测用户等同于真实活跃用户。不以虚构高并发作为选题理由。

## 11. 分阶段交付

1. 业务与原型：确认第一版规则，画商品详情、内容库和上架流程；准备少量真实文件。
2. 最小交易链路：一个测试店铺、一个商品、两个买家账号，完成测试购买与差异化下载权限。
3. 多商家发布链路：入驻、审核、店铺隔离、商品与版本发布。
4. 可靠性与售后：重复事件、失败恢复、退款、下架、更新边界。
5. 产品打磨：发现页、筛选、内容库、空状态、错误状态和部署验证。
6. 可选拓展：基础优惠券、AI 上架辅助或更细的版本权益，按剩余时间选择。

不承诺完成日期：开发开始前需了解课程截止时间、每周投入和现有基础。每阶段完成后保留可运行版本。

## 12. 毕设拓展路径

暂定题目：《面向数字商品的多商家交易与版本交付系统设计与实现》。最终题目以实现范围和导师要求调整。

主要深化方向：订单与权益一致性、文件版本发布与交付、权限和异常恢复的系统性验证。无需同时加入原创算法、微服务和 Agent。

可形成的论文材料：业务规则、状态转换、数据设计、权限矩阵、关键时序、异常实验与性能评估。课程原型是否沿用为毕设，后续独立决定。
