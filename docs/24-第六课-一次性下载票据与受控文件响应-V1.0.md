## 1. 用户点击后发生了什么

### 1.1 先操作页面

本地运行后，用买家账号完成一次测试购买：

1. 打开 `/library`。
2. 点击“查看可用版本”。
3. 点击“查看文件清单”。
4. 点击某个“下载文件”。
5. 页面先显示“正在核验…”，成功后播报“已开始下载……本次下载凭证已经使用”。

按钮不直接指向文件地址。浏览器实际执行：

```text
点击下载
  → POST 下载授权
  → 得到一次性 downloadUrl
  → GET downloadUrl
  → 浏览器把 Blob 保存成文件
```

### 1.2 第一段请求：申请授权

```http
POST /api/library/{grantId}/releases/{releaseId}/manifest/items/{manifestItemId}/download-authorizations
```

响应示意：

```json
{
  "ticketId": 1,
  "downloadUrl": "/api/downloads/随机原始token",
  "expiresAt": "2026-10-03T12:40:00Z",
  "filename": "basic-resume-template.html"
}
```

这一步需要 Session 登录和 CSRF token，因为 POST 会创建 `download_tickets` 记录。

### 1.3 第二段请求：消费票据

```http
GET /api/downloads/{token}
```

成功返回文件字节。相同 URL 再请求一次返回：

```json
{
  "code": "DOWNLOAD_NOT_FOUND",
  "message": "Download authorization or file was not found"
}
```

404 同时覆盖“票据不存在、已过期、已消费、属于别人、当前权益失效”等情况，避免外部用户根据错误差异枚举内部资源。

## 2. 前端：从按钮到 Blob

### 2.1 API 函数

文件：`frontend/src/api/library.ts`。

```ts
export async function createDownloadAuthorization(
  grantId: number,
  releaseId: number,
  manifestItemId: number,
) {
  return apiPost<DownloadAuthorizationResponse>(
    `/api/library/${grantId}/releases/${releaseId}/manifest/items/${manifestItemId}/download-authorizations`,
  )
}
```

这里出现的 TypeScript 语法：

- `grantId: number`：参数名后面的 `number` 是静态类型。
- `Promise<DownloadAuthorizationResponse>` 由 `async` 函数推断：函数现在返回一个最终会得到响应对象的 Promise。
- 反引号字符串 `` `...${value}...` `` 叫模板字符串，用真实业务 ID 组成路径。
- `apiPost<T>` 的 `<T>` 是泛型参数，告诉调用方 JSON 应该具有什么结构。

文件 GET 不使用 `apiGet<T>`，因为响应是二进制，不是 JSON：

```ts
export async function getAuthorizedDownload(downloadUrl: string) {
  const response = await fetch(downloadUrl, { credentials: 'include' })
  await ensureOk(response)
  return response.blob()
}
```

`credentials: 'include'` 让浏览器携带 Session Cookie。`response.blob()` 把响应体读成 Blob；Blob 是浏览器表示一段二进制数据的对象。

### 2.2 组件状态

文件：`frontend/src/components/library/DeliveryManifestPanel.vue`。

```ts
const downloadingFileId = ref<number | null>(null)
const downloadError = ref('')
const downloadNotice = ref('')
```

`number | null` 是联合类型：当前可以是正在下载的文件 ID，也可以是没有下载任务的 `null`。

模板用同一个状态处理重复点击：

```vue
<button
  type="button"
  :disabled="downloadingFileId !== null"
  :aria-label="`下载${file.displayName}`"
  @click="downloadFile(file)"
>
  {{ downloadingFileId === file.id ? '正在核验…' : '下载文件' }}
</button>
```

- `:disabled` 是属性绑定；任何下载进行时，清单内按钮都暂时禁用。
- `@click` 是事件监听。
- `条件 ? 值1 : 值2` 是三元表达式。
- 原生 button 可用 Tab 聚焦，并用 Enter 或 Space 激活。

### 2.3 浏览器保存文件

```ts
const objectUrl = URL.createObjectURL(blob)
const anchor = document.createElement('a')
anchor.href = objectUrl
anchor.download = authorization.filename
document.body.append(anchor)
anchor.click()
anchor.remove()
window.setTimeout(() => URL.revokeObjectURL(objectUrl), 0)
```

对象 URL 是浏览器为内存 Blob 创建的临时地址。`download` 属性指定建议文件名。点击后移除临时 `<a>`，并调用 `revokeObjectURL` 释放地址。

这里的箭头函数：

```ts
() => URL.revokeObjectURL(objectUrl)
```

表示“稍后执行这段没有参数的函数”。不能在 `setTimeout` 处直接写调用结果，否则会立即撤销。

### 2.4 成功和失败播报

```vue
<p v-if="downloadError" role="alert">...</p>
<p v-else-if="downloadNotice" role="status">...</p>
```

`alert` 用于需要立即获知的失败；`status` 用于不打断当前操作的成功信息。组件没有在外层再叠加一个 `aria-live`，避免同一消息被重复播报。

## 3. Controller 与安全边界

### 3.1 授权 Controller

文件：`DownloadAuthorizationController.java`。

```java
public DownloadAuthorizationResponse authorize(
        @AuthenticationPrincipal MeteorUserPrincipal principal,
        @PathVariable long grantId,
        @PathVariable long releaseId,
        @PathVariable long manifestItemId
) {
    return downloadService.authorize(
            principal.id(), grantId, releaseId, manifestItemId
    );
}
```

当前用户 ID 来自已认证 Session 的 `principal`。请求体和 URL 都不能提交 userId 来冒充别人。

三个 PathVariable 只是“用户想访问哪些对象”的待验证标识。Service 必须证明它们属于同一条授权链。

### 3.2 文件 Controller

文件：`DownloadController.java`。

```java
return ResponseEntity.ok()
        .contentType(MediaType.parseMediaType(file.mediaType()))
        .contentLength(file.content().length)
        .cacheControl(CacheControl.noStore())
        .header(HttpHeaders.CONTENT_DISPOSITION, disposition.toString())
        .header("X-Content-SHA256", file.sha256())
        .body(file.content());
```

响应头作用：

| 响应头 | 当前作用 |
| --- | --- |
| `Content-Type` | 告诉浏览器文件媒体类型 |
| `Content-Length` | 给出本次响应字节数 |
| `Content-Disposition: attachment` | 建议浏览器按附件下载，并提供 UTF-8 文件名 |
| `Cache-Control: no-store` | 要求中间缓存和浏览器不要存储受控响应 |
| `X-Content-SHA256` | 暴露本次可信摘要，便于客户端或排障核对 |

### 3.3 Spring Security 做了什么

`SecurityConfig` 要求两个下载接口都具有 `USER` 或 `CREATOR` 角色。授权 POST 还经过 CSRF 防护；文件 GET 不需要 CSRF，因为 GET 不创建新的票据，但仍需要 Session。

角色检查只证明“已登录且具有基础角色”。对象级授权仍由 `DownloadService` 完成。

## 4. 签发票据：随机 token、哈希和 V12

### 4.1 先重新查询可下载文件

`authorize` 首行调用：

```java
DownloadableFileProjection file = findAccessibleFile(
        userId, grantId, releaseId, manifestItemId
);
```

Mapper SQL 同时 JOIN：

```text
entitlement_grants
  → releases
  → delivery_manifests
  → manifest_items
  → file_objects
```

WHERE 条件至少包含：

```sql
eg.id = #{grantId}
AND eg.user_id = #{userId}
AND eg.status = 'ACTIVE'
AND r.id = #{releaseId}
AND r.status = 'PUBLISHED'
AND mi.id = #{manifestItemId}
```

Release 通过 `r.package_id = eg.package_id` 与 Grant 的可信 Package 连接。浏览器不能拿 Basic Grant 配合 Pro Release 或其他 ManifestItem。

### 4.2 生成原始 token

```java
byte[] bytes = new byte[32];
secureRandom.nextBytes(bytes);
return Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
```

- `SecureRandom` 用于生成难以预测的安全随机字节。
- 32 字节等于 256 bit 随机空间。
- URL-safe Base64 使用适合 URL 的字符，并去掉末尾 padding。

原始 token 只出现在返回给当前浏览器的 `downloadUrl` 中。

### 4.3 为什么数据库只存哈希

```java
sha256(token.getBytes(StandardCharsets.UTF_8))
```

如果数据库泄漏，攻击者看到的是 64 位十六进制 SHA-256，不能直接把它当下载 token 使用。消费请求把收到的原 token 再哈希，用哈希查询数据库。

这和密码存储仍有区别：密码来自低熵的人类输入，需要 BCrypt 的盐和慢计算；下载 token 是 256 bit 随机值，SHA-256 足以用于当前查找键。

### 4.4 同一个 Clock 生成两个时间

```java
Instant issuedAt = clock.instant();
Instant expiresAt = issuedAt.plus(Duration.ofMinutes(5));
```

`created_at` 与 `expires_at` 都由同一次 Java Clock 生成并显式写入，确保数据库约束 `expires_at > created_at` 不受应用时区与数据库默认时区差异影响。

### 4.5 V12 两张表

`download_tickets` 保存：

- token 哈希；
- 用户、Grant、Release、ManifestItem、FileObject；
- `ISSUED` 或 `CONSUMED`；
- 到期、消费和创建时间。

关键约束：

```sql
UNIQUE (token_hash)
CHECK (status IN ('ISSUED', 'CONSUMED'))
CHECK (
  (status = 'ISSUED' AND consumed_at IS NULL)
  OR (status = 'CONSUMED' AND consumed_at IS NOT NULL)
)
CHECK (expires_at > created_at)
```

`download_audits` 用 `UNIQUE(download_ticket_id)` 保证当前一张成功票据最多一条响应准备审计。

## 5. 消费票据：事务、行锁和二次授权

### 5.1 输入先做长度边界

```java
if (token == null || token.isBlank() || token.length() > 200) {
    throw new DownloadNotFoundException();
}
```

空 token 和异常长 token 不进入数据库查询。这里返回同一 404，不泄露更细内部判断。

### 5.2 `FOR UPDATE` 锁定票据

Mapper 查询：

```sql
SELECT ...
FROM download_tickets
WHERE token_hash = #{tokenHash}
  AND user_id = #{userId}
FOR UPDATE
```

`consume` 标注 `@Transactional`。两个并发请求使用同一 token 时，数据库让它们串行进入票据状态判断：第一个成功标记 CONSUMED，第二个随后看到已经消费并返回 404。

只在 Java 写 `if (status == ISSUED)` 不能单独解决并发，因为两个线程可能同时读到旧状态。

### 5.3 票据状态检查

```java
if (ticket.status() != DownloadTicketStatus.ISSUED
        || ticket.consumedAt() != null
        || !ticket.expiresAt().isAfter(now)) {
    throw new DownloadNotFoundException();
}
```

`isAfter(now)` 表示到期时间必须严格晚于当前时间。恰好等于当前时间已经过期。

### 5.4 为什么消费时还要再查一遍

票据签发后、文件 GET 前可能发生：

- Grant 被撤销；
- Release 被禁用；
- ManifestItem 关系被错误改变；
- 票据数据与当前 FileObject 不一致。

所以消费时再次调用 `findAccessibleFile(...)`，并核对：

```java
if (file.fileObjectId() != ticket.fileObjectId()) {
    throw new DownloadNotFoundException();
}
```

票据表示短时意图，不冻结五分钟内的永久访问资格。ADR-0002 选择了“消费时仍以当前授权状态为准”。

### 5.5 状态更新仍检查影响行数

```java
if (downloadMapper.markTicketConsumed(ticket.id(), userId, now) != 1) {
    throw new DownloadNotFoundException();
}
```

SQL 还限定 `status = 'ISSUED'`。行锁是主要并发控制，条件更新和影响行数检查继续防止异常状态下错误成功。

## 6. 文件完整性和审计语义

### 6.1 try-with-resources

```java
try (InputStream input = new ClassPathResource(file.storageKey()).getInputStream()) {
    byte[] content = input.readAllBytes();
    ...
}
```

圆括号中的 InputStream 会在代码块结束时自动关闭，包括读取异常。这个 Java 语法叫 try-with-resources。

### 6.2 当前只接受 CLASSPATH

```java
if (!"CLASSPATH".equals(file.storageProvider())) {
    throw new DownloadStorageException(...);
}
```

常量放左侧调用 `equals`，即使数据库值意外为 null 也不会抛 NullPointerException。未来接 S3／OSS 时应新增存储适配层，不应在前端判断 provider。

### 6.3 大小和 SHA-256 同时校验

```java
if (content.length != file.sizeBytes()
        || !sha256(content).equalsIgnoreCase(file.contentSha256())) {
    throw new DownloadIntegrityException();
}
```

字节数能快速发现明显截断；SHA-256 能识别内容变化。两者都不是授权，授权已经在前面完成。

当前使用 `readAllBytes()`，整个文件进入 JVM 内存，只适合 634 B、311 B 这类学习素材。生产大文件应改用流式响应或对象存储短时签名 URL，并设置大小、超时、Range、限流和连接中断策略。

### 6.4 先准备文件，再消费并审计

当前事务顺序：

```text
锁定票据
  → 二次授权
  → 读取并校验文件
  → 标记票据 CONSUMED
  → 插入 DownloadAudit
  → 事务提交
  → Controller 写 HTTP 响应
```

审计结果名是：

```text
FILE_RESPONSE_PREPARED
```

它只表示服务端已经准备好响应字节。服务器无法仅凭这一行证明浏览器完整接收并保存了文件，因此不能把它叫“下载完成回执”。

## 7. 失败路径、测试和真实证据

### 7.1 风险与防御对照

| 风险 | 当前防御 | 结果 |
| --- | --- | --- |
| 匿名申请或下载 | Spring Security | 401 |
| 已登录但授权 POST 无 CSRF | CSRF Filter | 403 |
| 别人的 Grant | `user_id` + ACTIVE 联合查询 | 404 |
| Basic Grant 配 Pro Release | Grant Package JOIN Release | 404 |
| 条目不属于 Release 清单 | Manifest JOIN ManifestItem | 404 |
| 票据过期 | `expiresAt.isAfter(now)` | 404 |
| 票据重复使用 | 行锁、状态、条件更新 | 404 |
| 签发后撤权／禁用版本 | 消费时再次授权 | 404 |
| FileObject 被替换 | ID、字节数、SHA-256 校验 | 404 或 500 完整性错误 |
| 存储读取失败 | `DownloadStorageException` | 500，`DOWNLOAD_STORAGE_FAILURE` |

跨用户、跨套餐和条目篡改都统一隐藏为 404；内部文件损坏返回明确的 500 错误码，便于监控区分授权拒绝和服务端数据故障。

## 8. 面试追问和准确回答

### 问：为什么分成授权 POST 和文件 GET？

答：

> POST 在 CSRF 保护下验证业务对象并创建短时一次性票据；GET 只消费已经签发的票据并返回文件。这样文件 URL 不包含 storage_key，票据可过期、可一次性消费，消费时还能重新检查撤权和版本状态。

### 问：数据库泄漏后 token 还能直接用吗？

答：

> 不能直接用，因为库里只保存原 token 的 SHA-256。原 token 是 SecureRandom 生成的 256 bit 随机值，只返回当前浏览器。消费时把 URL token 再哈希查询。这里不使用 BCrypt，因为高熵随机 token 与人类密码的威胁模型不同。

### 问：为什么有票据还要二次授权？

答：

> 票据有效期内 Grant 可能撤销、Release 可能禁用。系统把票据视为下载意图，不视为冻结的五分钟永久权限；消费时重新 JOIN ACTIVE Grant、PUBLISHED Release、ManifestItem 和 FileObject，因此尚未消费的票据会被当前授权状态阻断。

### 问：怎样防止同一 token 并发下载两次？

答：

> 消费方法在事务中按 token hash 和 userId `SELECT ... FOR UPDATE` 锁定票据；第一个事务完成 CONSUMED 更新后，第二个事务才能继续，并会看到已消费状态。更新 SQL还要求 status=ISSUED，并检查影响行数为 1。

### 问：下载审计能证明用户下载完成吗？

答：

> 不能。当前 `FILE_RESPONSE_PREPARED` 只证明服务端完成授权、文件校验并准备了响应。连接可能在响应传输中断开，浏览器也可能没有保存，所以审计命名刻意不写“COMPLETED”。

### 问：为什么当前实现不能直接用于大文件？

答：

> `readAllBytes()` 会把完整 Classpath 文件读入 JVM 内存。当前素材不到 1 KB，适合教学验证；生产大文件应换成流式传输或对象存储签名 URL，并补 Range、超时、限流、失败审计和传输中断处理，同时保留现有对象级授权语义。

## 9. 三分钟项目表达

先理解后改成自己的话：

> 在支付成功并创建 ACTIVE EntitlementGrant 后，内容库按当前 Session 用户逐层读取 Package Release 和冻结 Manifest。下载时前端不接收 storage_key，而是先以 Grant、Release、ManifestItem 申请五分钟一次性票据。服务端用一条 JOIN 查询同时验证 Grant 属于当前用户且 ACTIVE、Release 仍为 PUBLISHED、条目属于该清单，然后用 SecureRandom 生成 256 bit token，数据库只保存 SHA-256。文件 GET 在事务中按 token hash 和用户锁定票据，检查未过期未消费，再执行相同授权查询，防止签发后撤权或版本禁用仍能下载。读取 Classpath 小文件后核对数据库中的字节数和 SHA-256，成功才把票据更新为 CONSUMED，并写 FILE_RESPONSE_PREPARED 审计。前端用 Blob 触发浏览器保存，并为忙碌、成功和失败提供键盘可用按钮与状态播报。下载相关有 12 项测试；真实 MySQL 和 Playwright 验证了文件保存、重复 token 404、320px、44px 目标和 axe 0 违规。当前支付是本地测试适配器，文件只来自 Classpath 小素材，生产对象存储、大文件流和断点续传仍未实现。
